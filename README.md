# Zaratustra

Zaratustra — open-source продукт для длительных направлений работы, конкретных
задач и сохраняемого знания с участием человека и программных агентов.
Актуальная основа — **Core v0.1 / Activity**, версия пакета — **0.19.0**.

Один SQLite Core хранит предметные данные, права, адресные версии и квитанции.
Activity задаёт направление; Work — конкретную работу; Method — версионированный
способ исполнения. Source сохраняет полученный оригинал, Analysis — отдельный
разбор, Claim — утверждение с основаниями, Artifact — результат. Подготовка,
исполнение, внешняя доставка и приёмка владельцем — разные события.

Обычный локальный вход — `zaratustra`, использующий установленный пользователем
Pi из PATH. Назначенное исполнение использует тот же Pi RPC и DBOS; DBOS хранит
техническое состояние, а не вторую предметную базу. Старый Home/file-first backend
сохранён в истории, но не подключается как параллельный источник состояния.

## Установка и запуск

Проверенный контур: Windows, Python 3.13.7, Node 22.19.0, SQLite 3.53.3 и Pi 1.0.4.
Это граница фактических проверок, а не обещание проверки всех платформ и будущих
версий Pi. Программа, её конфиг, Core и рабочая папка выбираются отдельно.

Собрать wheel из этой ветки:

```text
uv sync --locked
uv build
uv tool install --force --from dist/zaratustra-0.19.0-py3-none-any.whl zaratustra
```

Для новой установки сначала подготовьте обычный Pi и свой конфиг:
[runbook](docs/core-v0.1/INSTALLED-RUNBOOK-20260927.md). Если конфиг уже существует:

```text
zaratustra bind --config <path-to-config.json>
zaratustra verify
zaratustra
```

После `CONNECT` доступен обычный разговор и инструменты Core. Выбор Activity/Work
делается через `/zara-work`; сохранённый разговор открывается через `/resume`.
Можно переопределить модель на один запуск: `zaratustra --model <model-id>`.
Доступные модели и провайдер зависят от собственной настройки Pi и аккаунта.
Секреты не помещаются в репозиторий, Project Instructions или материалы Core.

Версия 0.19.0 добавляет [общую память](docs/general-memory.md): каталог областей,
пакетное чтение, историю, проверяемый кэш и полный текстовый экспорт. При обновлении
существующей установки выполните `zaratustra upgrade` для явного перехода 12 → 13.
Личные сведения остаются в пользовательском Core.

Уже выбранную установку не нужно повторно `setup`/`bind` при обновлении wheel:
завершите процессы Zaratustra, обновите существующий uv tool, выполните `verify`
и запустите новый процесс. Windows может блокировать замену занятого launcher.
`upgrade` мигрирует схему Core, а не обновляет программу. Не пересоздавайте Core
ради замены программы. Обычный Pi обновляется отдельно от Python-пакета.

## Внешнее обсуждение и GitHub

При доступе внешнего чата к GitHub **основной источник меняющегося кода — репозиторий**:
https://github.com/ainazemtsau/zaratustra . Используйте актуальный `main` или явно
выбранную ветку. Постоянные Project Instructions содержат правила и маршрут чтения,
не копию текущего кода. Обязательный файл контекста Project и его ручное обновление
после изменений репозитория не нужны.

Начинайте с README, [руководства по интеграциям](docs/integrations.md) и относящихся
к вопросу файлов. Называйте действительно прочитанную ветку/commit, когда они известны.
GitHub не показывает неопубликованные изменения и локальные данные экземпляра.
При конкретном недостатке сведений внешний чат формулирует вопрос Code Agent;
пользователь переносит запрос и полный ответ. Текст/файл — запасной путь при отсутствии
доступа или для отдельных локальных сведений, а не обязательный журнал Project.

## Реализованный слой интеграций

`zaratustra.integrations` — общая граница установленных технических операций,
независимая от Pi и CLI. Каталог и контракты точны; пользовательские темы и цели
не ограничены списком. `zara_integration` доступен в обычном Pi; без модели:

```text
zaratustra integration catalog
zaratustra integration contract --adapter manual --operation prepare_document
```

Первый адаптер — **manual**: сохранить готовую индивидуальную инструкцию/контекст,
сохранить полный доставленный текст, прочитать точную ревизию окнами, получить
поставляемый обзор продукта. Обзор — дополнительный источник, не живой Core и
не обязательное приложение к Project. Существующие `zara_transfer` и `exchange`
сохраняют совместимость.

Skill `zaratustra-external` поставляется вместе с wheel и явно загружается launcher.
Настройка и история конкретной Activity остаются в Core, не в общем skill или docs.
Произвольный текст, отсутствующая дата и невалидный JSON внутри него не блокируют
сохранение. Сначала сохраняется оригинал, затем отдельно разбор и дальнейшие действия.

Подготовленный Handoff не означает отправки; сохранённый Source не означает факта,
разрешения исполнить предложение или acceptance Work. Автоматические API-коннекторы,
Trilium, браузерные роботы и фоновые внешние отправки пока не реализованы. Чтение
GitHub средствами внешнего чата не является новым API-коннектором Zaratustra.
Подробнее: [интеграции](docs/integrations.md).

## Разработка и проверки

Начните с [AGENTS.md](AGENTS.md),
[спецификации](docs/core-v0.1/Zaratustra_Core_Specification_v0.1.md) и
[политики выпуска](docs/core-v0.1/DELIVERY-POLICY-20260926.md).
Текущий результат и ограничения: [RESULT.md](RESULT.md).

```text
uv run --locked python -m tools.check --deliver
```

На Windows закреплённый SQLite runtime можно передать через `ZARATUSTRA_SQLITE_DLL`.
Полный gate проверяет hygiene, типы, импортные границы, тесты и сборку. Обычные Pi
traces используют localhost и синтетический провайдер; они проверяют механические
пути, не качество реального ответа модели или настройку внешнего аккаунта.
Публичная ветка не содержит новых частных отчётов экземпляра и не публикует его Core.
