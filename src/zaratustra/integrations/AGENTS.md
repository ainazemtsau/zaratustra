# Integration boundary

The installed `memory` adapter exposes catalog, batch, history, selection windows
and cache preparation through the public Core. It has no external transport.
The manual boundary may include explicitly selected organized memory from another
Activity, retaining its origin and checking rights; exchange Activity/Work anchors
stay separate. Managed selection writes require existing artifact-write authority.

Use only the public Core foundation. Never import Pi, release, legacy backends,
instances, tests or tools. Core owns durable state, rights, revisions and receipts.

Registry entries are trusted installed code with typed operation parameters, not
user scenarios or executable profiles. No eval, dynamic import from user input,
HTTP proxy, background worker, second queue, authority grant or shadow registry.
The shipped manual adapter has real prepare/retain/read operations and a static
product reference. It does not send externally, run workflows or accept results.
Unknown adapters/operations fail closed. Account capability reports are evidence,
not executable adapters. External text remains unstructured retained data.

Instance instructions/context are Source/Handoff/Analysis/Claim in Core. Updated
text creates another Handoff; no rewriting history. Exact byte reads are bounded.
Only text actually returned to the model contributes exposed Core references.
The catalog describes implementation, never the user's account or its permissions.
Future external-effect adapters need separately implemented authority, durable send
identity, outcome evidence and safe handling of uncertain sends before activation.
