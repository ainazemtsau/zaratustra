0.3. Language and interaction [U]

Zaratustra is English-first internally. Canonical instructions, technical documentation, record titles, working statements, plans, conditions, method instructions, and normal search formulations are English. The agent converses in the user’s language and persists an English Knowledge preference describing that language. Russian is one supported conversation language, not a global product setting. Language understanding, English formulation, query expansion, and user-language replies belong to the model; no translation service is needed.

The user interacts only through conversation with the agent. The user is never required to inspect or edit records, IDs, JSON, schemas, directories, service files, dashboards, or maintenance commands. Catalog, diagnosis, export, backup, and restore are agent capabilities whose results are explained through chat. One-time host/package installation is described separately from daily product use; technical commands are operator/developer instructions, not a second product UI.

Original Evidence is distinct from its English working representation. Preserve original files and exact quotes, names, paths, identifiers, code, and externally meaningful strings. Mark an English paraphrase/translation as derived, keep its source ref and language, and never present it as an original quote. An English statement can describe a Russian source without changing that source. Search may use original-name aliases; canonical working language does not require anglicizing a person’s name.

1. Product and release boundaries

1.1. User outcome

Zaratustra is a durable workspace for a personal agent. Through natural conversation the user creates and continues different activities, keeps materials and shared knowledge, receives plans informed by relevant context, corrects mistakes, reuses methods, and learns from outcomes. Pi and a capable model perform dialogue, understanding, planning, context selection, and semantic judgment. Zaratustra supplies addressable persistence, coherent changes, versions, controlled access, and inspectable results.

1.2. Complete R1

R1 includes all eight record kinds; Activity and durable Work; nested plans, dependencies, waits, pause/resume and reopening; retained materials and addressable reading; shared memory, catalog, relations, lexical and structural retrieval; provenance and correction; manual handoffs and late/partial results; versioned Methods and Runs; addressed Evaluations and unresolved Signals; new-process continuation; diagnostics, export, backup, verified restore; archive and deletion with retention safeguards. Meaningful facts and explicit corrections persist during normal work. A candidate Method can be created and reused before Sleep exists.

Platform and material-format coverage are concrete proposals awaiting Q1–Q2, not silent reductions of R1. A failed or unavailable live criterion stays unverified. Storage tests alone do not make the product ready.

1.3. R2 and the next harness

R2 adds Sleep as a complete, explicitly initiated procedure over the same Core: review accumulated cases and open problems, propose bounded changes to knowledge/catalog/methods, observe later use, and maintain storage. Its progress survives interruptions. A scheduler, daemon, automatic wake-up, and external delivery service are not prerequisites. Codex follows Pi as a separate integration; it must not require changing the meaning of existing records.

1.4. Exclusions and historical code

No Letta dependency, second agent runtime, mandatory vector/graph service, universal workflow engine, permanent daemon, multi-user shared database, cloud multi-writer SQLite, model weight training, autonomous executable installation, dashboard, or automatic migration of old Zaratustra. Embeddings can later provide additional candidates, but cannot replace navigable memory and provenance. Old product branches may be read as specific evidence when authorized; they are not mandatory implementation foundations.

4. Data model: eight primary kinds

The primary kinds are Activity, Work, Evidence, Knowledge, Method, Run, Concept, and Entity. Versions, relations, Evaluations, Signals, approvals, operation intents, receipts and Changes are supporting structures, not extra semantic memory kinds. Use normal tables where appropriate rather than one ever-growing JSON object.

Applicability belongs to the claim/method/work conditions, not visibility. The default is one personal workspace. Restricted access protects managed Core surfaces, not against a same-account shell (§19.3). Original names, quotes and identifiers remain unchanged under the language rule.

4.2. Refs and versions

A current ref is {id}; a historical ref is {id, revision}; a Method ref is {id, content_version}, optionally also revision. schema_version concerns storage/export, not a method. New objects in one transaction can be addressed by {client_ref}; Core returns permanent mappings. Ref target kinds are validated. A historical ref never silently follows a current redirect or returns modern text as old. Missing retained content returns CONTENT_NOT_RETAINED.

4.3. Activity

Required: purpose and status (active, paused, closed). Optional: local rules, material refs, local metric definitions, related Activity refs. Activity is a durable domain of work, not a model process, session, or folder. Independently useful information is not hidden only inside its prose. Closing preserves shared knowledge and exposes unfinished Work. Pausing suppresses automatic continuation, not acceptance of new materials. Merge/split requires an explicit user decision and preview of moved Work/conditions; historical Runs keep their origin.

Unclear “tomorrow” is interpreted from known timezone and explained or clarified. Work is waiting only when no independent step is available; a waiting step alone need not stop the whole Work. Blocked means a problem requiring intervention rather than a normal expected input.

4.5. Evidence

Evidence preserves a source or material, without claiming its truth. Fields: source_kind, source_locator, captured_at, event_time if known, content_hash for retained bytes, retained_excerpt and/or blob_ref, availability, trust_origin, source_language, optional parser/version and derived_from Evidence ref. Kinds include user message, tool result, imported file, external reply, generated artifact. Model conclusions belong to Knowledge with inference basis; a generated artifact may be Evidence of what was generated, never of its own correctness.

Availability: retained, locator_only, missing, deleted. A path or URL alone does not promise durable content. For durable reading retain a managed immutable copy. Large-material extraction is a derivative tied to exact source bytes and parser version, with chapter/page/character-range locators. Original content remains in its language. Unsupported, scanned, encrypted, damaged, or oversized input produces a specific limitation, not invented text. Proposed format coverage is in Q2.

4.7. Method

Fields: applicability, instructions, input_contract, expected_output, context_requirements, dependencies, tool_requirements, content_version, state (candidate/active/deprecated), derived_from, limitations. A first candidate may follow one clear case or explicit instruction; success count is no universal threshold. Active is a working selection, not proven general usefulness.

Behavioral content includes instructions, applicability, required inputs/outputs/dependencies and safety conditions. Its change increments content_version. Rename/status-only change increments revision. Work bindings such as a project path do not create a new Method version. Changed sequence or check criteria do. Resolve dependencies to exact versions for each application; reject dependency cycles in R1. Prefer a short independent local Method with derived_from over a layered override framework.

4.8. Run

A Run is a meaningful episode, not every message or a long-lived objective. Fields: optional work_id, mode (work/conversation/correction/sleep), case_id, execution (running/completed/failed/interrupted), times, factual summary, result refs, method invocations, important starting versions, local metrics, Evaluation/Signal refs, environment_ref. Waiting belongs to Work, not a second Run lifecycle.

Useful Knowledge can be saved directly from Evidence without a Run. case_id groups continuations of the same substantive case; retries and late feedback do not become new independent successes. Core provides addresses and technical deduplication, not proof of statistical independence. environment_ref records actual package, bootstrap/skill versions, provider/model identifiers and relevant available parameters; unknown stays unknown.

A Method invocation records method_ref, invocation_id, input_refs, output_refs, reported_application and any technical receipts. Retrieval is a separate trace. Reading a method does not prove following it; reported adherence remains a model report unless externally observed.

4.9. Concept

Fields: definition, aliases, broader_ids, status (active/merged/retired), redirect_to for merged, optional boundary notes. Multiple broader parents are allowed; cycles are not. A broader relation is navigation, not inheritance of all factual properties. Aliases mean alternative names of the same concept; related and broader do not mean identity. English labels and useful original-language aliases are compact agent search aids. Create categories only when actual content/navigation needs them; do not prebuild an ontology of human life.

4.10. Entity

A concrete identifiable person, device, place, organization or item. Fields: entity_kind, aliases, disambiguation, optional external IDs, status and redirect_to for a confirmed merge. Preserve authentic names and identifiers. Entity has no competing canonical store of personal facts; those are Knowledge referencing it. Similar names are candidates for identity resolution, not proof. Ambiguous sources may remain unresolved until identity matters. Merge of real persons/items needs explicit confirmation or a strong verified identity basis within the agreed policy, with an inspectable reversible proposal.

5. Relations, evaluations, signals, and Changes

5.1. Relations without duplicate truth

Structural relations derive from typed fields: Work membership/parentage, classification, Method dependencies/use, evidence_refs, supersedes_refs, Evaluation.target_ref. Do not duplicate these through put_relation. Additional navigation relations include related, relevant_to and derived_from; meaningful links carry a reason. Evidence relations include supports, contradicts, supersedes and evaluates with validated endpoint kinds/versions. A separate supports/contradicts link is allowed when it expresses an independent addressed relation absent from a typed field. Registered direction/symmetry and endpoint constraints apply. Related does not imply execution dependency or causality.

5.2. Evaluation

Supporting addressed record: evaluation_id, target_ref, assessment (helpful/unhelpful/mixed/unknown), dimension, basis, evidence_refs, recorded_at, event_time, optional supersedes_evaluation_id and explanation. Dimensions distinguish owner usefulness, a concrete criterion, technical operation and named local metrics. Bases distinguish user feedback, observed criterion, test result and model assessment. A test pass and an owner’s “inconvenient” can both stand. No aggregate score erases that distinction.

Late feedback points to the old result/version, even when recorded today. Corrected feedback supersedes the old Evaluation rather than creating another method attempt. Verified provenance of “not helpful” does not verify the model’s diagnosis of why.

5.3. Signal

Stable address run_id/signal_id (or an equivalent supporting-row ID); fields kind, subject_refs, evidence_refs, description, problem_state, reviews, next_check. Kinds: problem, correction, possible_regression, useful_result, novelty. States: open, observing, resolved, dismissed. Observing requires an applied change ref and a future check condition. Resolved requires grounds; dismissed a reason. Review history is independent of state: considered can remain open. Referencing a Method identifies the subject, not the cause. Open problems pin minimal origin evidence. Grouping similar signals does not prove independent cases.

5.4. Change and rollback

Change records transaction_id, changed refs and before/after revisions, trusted actor, reason, caused_by and Core time; monotonically increasing change_seq supports cursors. Knowledge/Method causes point to a source or exact instruction; migration points to its version. This is current-state storage with retained versions, not mandatory full event sourcing. Retain versions needed by open Work/Signals, current methods, declared audit history and safe rollback. Missing old bodies are explicit. Rollback creates a new revision after checking current dependencies; it does not rewind the whole world. Large unapproved semantic change can remain a draft Work and addressed Signal.

6. Provenance and source handles

6.1. Transport is not the speaker

Pi 1.3.0 declares input.source as interactive, rpc or extension. A user-role run can be a submitted prompt, RPC prompt, or pi.sendUserMessage(). Therefore neither message.role=user nor before_agent_start.messageType=user certifies human authorship. Capture technical origin at input/known tool boundaries and retain the limitation. See the pinned Pi declarations.

6.2. Capture contract

A source capture records transport, available channel/controller identity, workspace and runtime/session, stable source ref, capture stage, exact observed text/bytes or retained excerpt and digest, source language, time, and derivation links. A verbatim excerpt must match the captured source; an English working paraphrase is labelled as such. Model-supplied actor/user_feedback flags are never trusted.

Pi input handlers run in order and may transform content; this handler can see a prior extension’s transformed text. Thus “observed at this hook” is not automatically “original keystrokes.” In the supported deployment, capture before transforming extensions or use a trusted ingress that provides original and transformed forms. If that cannot be established, retain the observed stage, mark original unavailable, and do not certify the transformed text as exact owner approval. Before-agent-start prompt expansion is not a substitute for original capture. This is a deployment check, not a new transcript system.

6.3. Lifetime and durable evidence

A source_handle is an opaque capability issued by the adapter/Core registry for exact captured content, workspace, source ref, session/runtime and allowed use. It is not the string “current user” resolved to whichever message happens to be latest. Default transient handles expire on runtime reload, session replacement, shutdown, restore epoch change or revocation. Pending handles cannot be rebound to new content. Retained Evidence and stable source refs survive; trusted reattachment can issue a new handle for that exact retained source, without creating current owner authority.

Stable source refs, rather than ephemeral handle strings, participate in commit payload identity. Replay of an already committed request returns its receipt after current access checks and need not resurrect an expired handle. A genuinely new write must resolve valid handles. Restored historical approval or source text never authorizes a new consequential action by itself.

The request-local snapshot is refreshed before the next model call (§14). Old tool messages remain historical and are not current authority. Core cannot infer every semantic consequence of a corrected statement.

7. Catalog, lexical search, and discovery

7.1. Agent navigation

zara_map gives bounded entries into existing memory: people, resources, topics, work, methods, materials, experience and unfiled. They are query views, not extra stores or fictitious personal facts. Each entry has English label/description, a ready selector and continuation indication. A selector is exactly a registered view or returned record ID. The user never handles selectors.

Read progressively: entry/section → nearby cards → selected full records and source ranges. Browse is not an unbounded recursive graph dump. Related edges do not traverse the entire network. Origin Activity can aid ranking but never silently limit shared memory. The trusted principal determines which entries, cards, counts and links are visible.

7.2. Two independent discovery paths

Navigation finds unknown names through actual sections and categories. Lexical search finds textual candidates even after bad classification. Combine them as needed: search a term and inspect parents/claims, or browse a section and search within it. A missing structured predicate must not make a textual claim invisible. Structural filters can select kinds, concepts/descendants, subjects, objects, predicates, status and time; the model reads residual natural-language conditions.

7.3. English lexical baseline [D]

Recommend SQLite FTS5 with an English working-text index using porter unicode61, plus unicode61 matching for authentic names/identifiers/aliases where stemming would lose precision. Index canonical titles/statements/method text, useful English extraction summaries and registered aliases; original excerpts remain separately addressable and need not be translated wholesale. The official FTS5 contract provides English Porter stemming and query syntax; it is lexical retrieval, not semantic understanding.

The API accepts plain term/phrase inputs with explicit match mode (all terms, any terms, or phrase), and typed filters. It does not execute arbitrary model SQL or treat user punctuation as FTS operators. Bind the generated MATCH expression as a SQL parameter. Quote each literal term/phrase for FTS and double embedded double quotes; SQL binding alone does not escape the FTS grammar. Raw AND/OR/NOT, parentheses, colon, asterisk and quotes in names are data unless the API deliberately constructs a registered operator. Optional prefix search is a separate bounded flag applied after validation. Empty/tokenless or over-limit input returns a validation result, not an unrestricted scan. Test English inflections, names, apostrophes, hyphens, C++, quoted strings, non-Latin aliases and hostile syntax.

Aliases preserve alternative names for the same Concept/Entity; they are not an exhaustive thesaurus and do not prove identity. The model expands an English query with useful synonyms, singular/plural terms, broader topics or known original names, and records that expansion in retrieval trace. If a first query misses, inspect a broader branch or alternative text. No custom NLP, Russian morphological subsystem, embedding service or translator is required.

7.4. Cross-language acceptance

A Russian conversation provides a fact. Evidence keeps the Russian words; Knowledge contains an English working statement. In a later process with no old transcript, a different Russian request does not name the resource. The model navigates English memory or formulates English search terms, reads the correct English claim plus original grounds/conditions, and answers in Russian. A separate badly classified fixture verifies English lexical fallback. Do not seed the answer or the needed English phrase into the test prompt. T07–T10 and T43 cover this behavior.

7.5. Growth, revisions, and honest limits

A Concept is reused, aliased, refined or created only after checking nearby existing structure. New categories explain their distinction; do not create a node for every noun. Summaries route to addressed sources rather than creating ungrounded personal claims or chains of summaries treated as independent evidence.

Every page returns applied_filters, has_more, next_cursor, catalog/index generation and warnings. Exact total is optional; approximate counts are marked. Cursors bind query, order, access scope and generation. Invalidated continuation returns CURSOR_INVALIDATED. Do not keep an SQL transaction open while the model thinks. Use keyset pagination plus explicit invalidation as a simple default; a different safe strategy needs evidence. No fixed discovery-step count is promised at unlimited scale.

Archive cards remain discoverable with visible archive status; large archived bodies are not automatically loaded. Historical mode is explicit. Empty or incomplete results are not proof of absence. Expand when relevant, then explain the remaining limit or ask for missing information.

7.6. Catalog reorganization

Rename preserves IDs. Merge leaves current redirects and aliases; historical refs stay on their original identities. Split creates new concepts and explicit memberships; the original may remain a broader section. Preview touched records/edges and validate final cycles/revisions. Large reorganizations use a staged new catalog generation with atomic switch or a visible maintenance Work with explicit incomplete state. They never appear completed midway. Real identity merges and semantic bulk changes follow approval policy; Sleep gets no universal administration right.

Attach partial inputs to exact waits/steps. One report section does not satisfy a whole-report wait, while an independent action may proceed. Late input is compared against original instruction, current goal/constraints and completed actions before changing the plan.

9.4. Completion is not usefulness

A completed Run is an ended episode. Work done means its acceptance is met. Owner usefulness is a separate Evaluation. “Create an Activity” can be checked by persisted state and new-session discovery; “be a useful personal assistant” needs actual owner experience. 10. Manual handoffs and bounded external actions

10.1. Manual handoff

Prepare an artifact with objective, current conditions, minimum necessary source context, expected result, handoff_id and Work/snapshot refs. The agent explains it in chat and supplies the artifact for the user to transfer. The user never needs to type its internal ID. Permission to read memory in Pi is not permission to send it to the recipient. Preparing the handoff is not sending it or proof of external execution.

On return, preserve the response as external Evidence. Match to the original request; if an internal ID is absent use contents to identify candidates and clarify material ambiguity. Compare original and current plan/conditions before accepting changes. Preserve useful analysis even if an action is obsolete. External message/request IDs permit delivery deduplication where trustworthy. Equal text/digest alone only suggests a duplicate; it cannot merge distinct events or create another successful method application.

10.2. Effect state and authority

A managed effect receipt contains operation_id, Work/step and relevant plan version, exact target/action, request_key if supported, preconditions, approval ref when required, state, observations and source refs. States: not_started → requested → confirmed; requested may become unknown; unknown becomes confirmed or confirmed_not_performed only on sufficient evidence. Confirmation records the actually verified postcondition; a currently matching file does not prove who wrote it. A new attempt after proven non-execution has an explicit link and newly checked authority.

Record intent before dispatch. Timeout, abort after dispatch, or lost response means unknown. Never auto-retry a non-idempotent action from that state. An external idempotency key helps only when the actual executor honors it. Claims, receipt IDs and a model promise cannot create exactly-once semantics outside Core.

10.4. Recovery scenarios

  • Inject interruption after an ordinary controlled file write but before receipt. The next process inspects the file and records an observed outcome; it does not blindly write again.
  • Inject interruption before dispatch with a durable intent. Establish dispatch/non-execution only if the retained evidence supports it; otherwise stop at unknown.
  • Prepare a manual handoff, change its Work goal, then return/re-deliver a partial response. Useful content persists without restoring the obsolete plan or duplicating cases.
  • Restore a backup taken before the file operation, so it has no receipt or intent. The restore barrier must still stop automatic execution of the restored step and require current-world inspection (§18.4).
  • Use an opaque command as a negative control: missing execution evidence must not turn into a claim of safe deduplicated retry.

11. Methods: reuse, composition, and correction

The model discovers a Method, reads its exact version, checks applicability and inputs, retrieves required current context, plans the Work and executes real tools. Run connects that invocation to the case and results. A necessary deviation is explicitly reported, not counted as exact compliance.

A Method may refer to other methods and expected sub-results. The model interprets the composition; Core resolves versions and rejects cycles. Resolve the complete selected dependency closure before its application and record it. Dynamically chosen submethods are pinned at choice time. Updating the general method does not rewrite old receipts or silently update local variants; review compatibility. No custom workflow programming language is required.

Context requirements can name exact refs or a dynamic category/selector and retrieval procedure. They do not permanently load every related fact. Package work/memory/Sleep skills are trusted entry instructions. Accumulated Methods remain in Core. A managed SKILL.md export carries Method ref, version and content hash; external edit is drift requiring explicit import or regeneration. Installation of generated scripts/extensions is development with code/dependency/rights/tests review, not automatic promotion of a useful textual method.

12. Sleep and accumulated experience — R2

Sleep is an explicit user conversation such as “Review accumulated experience,” using the same Pi extension and Core. A multi-session review has its own Work; Run.mode=sleep. Reviewing past outcomes is not another application success for the reviewed method.

12.1. Durable coverage

Read new meaningful Runs/Changes, new Evaluations, open Signals and pending checks. Use change_seq rather than event_time alone so a late evaluation is new input. Each bounded batch fixes a high_watermark. In the same transaction save dispositions, explicit deferred continuations and the cursor. Progress means every covered event was considered or deferred by address. Crash/retry cannot skip a batch. New-input coverage and unresolved problem queries are independent. A considered open Signal remains visible.

12.2. Procedure and improvement

  1. Get a bounded batch and its coverage/limits.
  2. Read the original goal, result, selected versions, grounds and current conditions for each selected case.
  3. Separate observations from causal hypotheses.
  4. Choose the smallest supported correction to knowledge, catalog, method or plan, or keep the problem open.
  5. Validate dependencies, revisions and authority; present material goal/priority/identity/bulk changes for approval.
  6. Save reason, change ref, expected benefit, limitations/regression risk and a concrete trigger for later checking.
  7. Archive/compact only content not pinned by open obligations and verification.

A missed week is one review of actual accumulated input, not seven fabricated daily events. Subsequent suitable Work records the method version actually used and separate owner, technical and model assessments. A later application alone does not resolve the Signal. Worse results may lead to compatible rollback, narrower applicability or a new diagnosis; negative trials remain. With insufficient evidence the outcome is unknown, not compulsory improvement.

12.3. Finite operation

Owner decision, 22 October 2026: Sleep has no total USD, token, attempt, dispatch, case, time or continuation budget. Each explicitly requested review is finite by its frozen initial input membership/high-watermark. New arrivals wait for the next explicitly requested cycle; no self-restarting cycle or recursive mining of Sleep bookkeeping. Normal per-call validation and pagination remain, with ten routing cards per technical batch by default, without limiting total review work. Abort preserves committed changes and addressed remainder; an explicit restart reviews retained eligible material. Keep complete actual usage, errors and attempts without reset. Scheduler and external notifications stay optional future capabilities.

13.5. Commit sequence

  1. Authorize access to the operation and check whether its request ID already has a receipt; a replay cannot reveal inaccessible content.
  2. Resolve valid sources and file stages outside a long SQL transaction; for a new call retain a compact prepared technical intent before uncertain dispatch/return boundaries.
  3. Begin a short transaction and repeat request-ID, access, epoch, revision and preview/approval checks under serialization.
  4. Resolve client refs and validate the final linked state, types, cycles and required grounds.
  5. Write domain records, retained versions, relations, Evaluations/Signals, Change sequence, index generation and the committed receipt atomically; mark the intent committed in that transaction.
  6. Commit, then return success. A lost response or abort after commit does not undo it.

Prepared intent is technical recovery metadata, not a partial domain success. It records normalized payload/digest, stable source/target/Work/step refs, request_id, initiating session/epoch and state. No LLM, external action or human wait occurs inside the domain transaction. Concurrent same-ID requests recheck uniqueness inside it.

13.8. New-session recovery without the old request ID

  1. Read the relevant Work/step, current state and bounded recent operation intents/Changes; alternatively find affected Activity/Entity/material and its Changes through normal catalog/search.
  2. Use structural anchors: original stable source ref, exact Work/step/plan revision, target refs, normalized operation digest, created-ID mapping and transaction links. Text/title similarity only finds candidates.
  3. If a committed receipt and Change identify the requested operation, read its actual result and continue from it without creating a replacement transaction.
  4. If an exact prepared intent has no receipt, inspect current authorized receipts/Changes and targets; an absent receipt establishes non-commit only within a known intact current database lineage. Reuse that intent/request ID only after establishing its identity and status.
  5. When anchors do not identify a unique operation, show the substantive alternatives through chat and ask for clarification. Do not silently merge similar requests or replay a guessed mutation.
  6. If restore/lineage uncertainty applies, do not infer that an old external action was unperformed or that post-backup commits never occurred. Apply §18.4; reconcile real effects and explain lost database history.

This uses Core’s existing IDs, guarded intents, receipts and Changes. No fuzzy-text “exactly once,” permanent transcript mirror, or second event-sourcing engine is needed. T19 and T41 explicitly test a fresh process that has lost the request ID.

Update affected FTS/catalog indexes in the same domain transaction or expose a checked generation barrier; stale search cannot return superseded as current. Search indexes are rebuildable. Use normalized UTC comparison, foreign keys and explicit domain validation. Keep native loadable SQLite extensions disabled unless separately justified.

16.3. Transaction and file boundary

SQLite handles local atomicity, not arbitrary files/services. WAL journals belong to the database protocol: do not copy an active .sqlite alone. Use short transactions and explicit busy handling; never hold a database transaction while waiting for the model. One-writer policy and logical Work claims remain separate from SQLite locking.

16.4. Migrations and export

Version schema/relationship vocabularies deliberately. Before migration verify supported source version, backup and absence of conflicting execution. After migration check integrity, foreign keys, domain refs, search and materials. Repeat migration detects already applied state. An older program must not write an unknown newer schema. Failure never deletes the database to start empty. Local metrics may extend through named type/unit/scope definitions, not arbitrary schema bypasses.

Agent export is a versioned machine-oriented manifest plus JSON and optional readable Markdown explanation, with workspace identity, refs, availability and exact included blobs. The user requests it in chat; manual editing is not required. Import is not implicit synchronization. Git may store code or deliberately exported Methods; no Git commit per utterance and no substitution of Git for SQLite/material backup.

Zaratustra trusted setup controls workspace location, budgets, managed scopes, retention, importer coverage, one-writer policy and backup destination. Retrieved documents and model tool arguments cannot redefine these. No second model chooser, provider registry or credential store. Through ordinary conversation the user can ask what is saved, what comes next, what waits, why a method changed, which source was used, whether memory works, or request an export/backup/restore. 18. Materials, backup, and restore safety

18.1. Import and crash safety

  1. Resolve a permitted source/path and verify real path, file type, size and allowed root; reject traversal/symlink escape before reading.
  2. Copy bytes into staging, calculate real digest/length and finish durable file writing.
  3. Move completed bytes into an immutable managed location in the same storage domain, using a supported atomic rename where available.
  4. In a short database transaction create Evidence and refs only to the completed available blob.
  5. Return committed success. Record parser-derived ranges against that exact source version, without changing original bytes.

The file operation and SQL transaction are not one atomic transaction. Crash before metadata commit can leave an orphan blob; later GC checks references, staging and backup pins before removal. Crash after commit must not leave a ref to an unfinished file. Flush/fsync, rename and Windows lock behavior require real fault tests; logical correctness does not prove protection against every hardware power failure. Identical bytes may share a blob while distinct provenance Evidence stays separate.

18.2. Format proposal, not assumed approval

Q2 proposes UTF-8 text/Markdown plus text PDFs and unencrypted EPUB for full R1, with ordinary small parser libraries and addressed ranges. First block needs only text/Markdown. Unsupported formats may be retained as opaque original bytes with an explicit “not readable/extracted” status; that does not satisfy the readable-material criterion. Scanned PDFs/OCR, DRM/encrypted EPUB, DOCX and other formats require separate coverage decisions. Do not write a new document parser or add an NLP service merely to avoid selecting a library.

18.3. Consistent backup

Use a supported SQLite consistent backup and derive the required blob manifest from that completed backup, not from a later changing live query. Protect candidate blobs from GC for the whole operation, copy the exact referenced set, then verify the resulting bundle. This combines SQLite’s database snapshot with our immutable-file manifest rather than claiming one filesystem transaction. Include schema, workspace identity, captured sequence/time, component lengths/digests and completeness. Do not include credentials or runnable transient claims. Missing/corrupt materials make the result explicitly incomplete. See SQLite Backup API and WAL constraints.

18.4. Restore must not replay the world

  1. Restore into a new quarantine directory. Verify actual component digests, supported schema, SQLite integrity/foreign keys, domain refs, retained versions, material availability and rebuilt indexes. Do not switch on partial success.
  2. Obtain chat approval for the exact backup identity, destination, coverage/loss warning and switch preview. Preserve the current workspace until the switch is verified; stop conflicting writers.
  3. At switch, create a new active restore epoch in trusted control metadata outside the restored snapshot. Bind subsequent CallContext to it. Invalidate restored session claims, transient source handles and old approvals. Record the restoration and recovery barrier before enabling managed continuation.
  4. Treat every restored Work/step that could repeat an external action as requiring reconciliation, even if the backup contains no effect receipt or prepared intent. Absence is expected when an action happened after backup; it is never proof of non-execution.
  5. Inspect current external state and any independent surviving evidence: actual controlled output bytes/version, a reliably queryable external postcondition, retained current-installation receipts if present, or an explicit owner report with honest provenance. Backup contents alone cannot clear the barrier.
  6. Clear the barrier only for a named action/Work with current postconditions, fresh guards/authority and an explained disposition. If non-execution cannot be established, remain unknown. A user may explicitly choose a risky repeat after the consequence is explained; record that decision rather than claiming safety.
  7. Permit read-only recovery and demonstrably independent new work. Do not disable all useful memory indefinitely, or globally mark every historical effect unperformed.

Counterexample driving this rule: backup at A says “write the report next”; the report is written at B; current storage is lost; restore A contains no B receipt. A receipt-only scan incorrectly repeats the write. An epoch and blanket reconciliation requirement for resumed effectful work catch it without an external receipt service. The new epoch is a local restore marker, not an external-world ledger. It cannot prove that nothing happened.

All supported restore/copy/import-as-active paths use this barrier, including transfer to a new machine. Raw replacement of database files outside the protocol is unsupported; consistency/identity mismatch stops writes, but no claim is made that all undetectable manual rollback can be identified. Restoring memory loses post-backup database history even when real-world files remain. Explain that distinction through chat. T25 must include the no-receipt case, not just restored known receipts.

18.5. Local device boundary

R1 is a single-user local workspace, not a live multi-device database in a network/cloud-synced folder. Move only a closed verified backup through an explicit operation. Multi-device merging needs a future conflict contract. WAL is not a distributed multi-writer mechanism. A designated backup can be copied as an artifact; credentials remain in Pi/OS configuration.

19.3. Minimum approval mechanics

  1. Core prepares an immutable preview_ref over a canonical finite change/action set: workspace and active epoch, exact targets and proposed values/deletions/recipient payload, required rights, relevant before revisions, policy revision, intended effect and expiry/revocation condition.

  5. Consume a one-operation approval atomically with the authorized Core commit/managed dispatch intent, retaining its receipt. Returning the same commit receipt is not a second use; a different payload/new action cannot reuse it.

A short preview/approval record built from existing guarded intents/receipts is necessary because neither a prompt instruction nor a raw “yes” identifies which changing operation was approved. With ambiguity, ask again before acting. No signature infrastructure, universal authorization server or new workflow language is needed in the single-owner local case. Unrelated record changes outside declared material dependencies need not invalidate a preview; missing a material dependency is a contract defect. Restore/reload/session replacement invalidates transient pending approvals; re-present preserved drafts without treating old words as new permission.

19.4. Actual security limit

Core access policy and approval are managed-surface controls. Pi/extensions run with process permissions; a same-user shell can access files/SQLite outside Core. A plugin cannot prove isolation from arbitrary or malicious peer extensions. A stronger boundary needs an OS sandbox/VM/separate account and restricted tools. Q3 proposes the personal trusted-desktop profile initially; do not call restricted fields an OS security guarantee. See official Pi safety guidance. Minimize personal information in transfers and diagnostics; retain no credentials as Knowledge. Secret detection is useful but not proof of perfect removal from arbitrary text, Pi history or backups.

19.5. Consciously selected provider [U]

The model/provider the user consciously chooses in Pi may process the user-supplied and ordinarily retrieved permitted context. Credentials and model selection remain Pi’s responsibility; Zaratustra introduces no duplicate model configuration or approval on every memory read. A different service, external assistant or delivery destination needs separate transfer authority even if a model provider already processed the same information.

A change of provider may send the already loaded transcript—including previous tool outputs and personal data—to the new provider, even without a new Core read. Explain this consequence when asking about an uncertain switch. Compaction is not a confidentiality purge. For deliberate native Pi selection, use verifiable choice evidence where available; do not infer it merely from model_select.source=set/cycle/restore, which is technical metadata and can also follow programmatic selection.

Zaratustra itself never changes the user’s provider/model. If a new selection cannot be traced to the user’s choice or an explicitly delegated bounded selection policy, mark processing authority unresolved, stop new managed retrieval and request ordinary-chat confirmation for the selected recipient and existing-context scope. Use supported abort/stop for an active affected run where available. Do not claim that blocking future reads removes already loaded context or that a notification event can reliably veto every request from another extension.

The supported trusted deployment must have no unconsented automatic model-routing extension; qualifying any such extension requires a verified pre-transmission gate or an explicit owner-delegated recipient policy. If installed Pi events cannot ensure that gate, the simpler supported solution is to leave automatic switching disabled and report this combination unsupported. Do not pretend a throwing observer or event.source establishes consent. User-confirmed recipient processing is a scope fact tied to the actual Pi selection, not a second chooser. T44 tests both native deliberate change and an extension-triggered unexplained switch, including already loaded transcript.

20. Retention, archive, and deletion

Open Work, unresolved effects, open Signals, observing corrections and their minimal grounds are pinned against automatic deletion. Exact Method content remains while an obligation or declared check needs it. A library source can be explicitly retained indefinitely regardless of access frequency. Rarity does not imply low value.

Archive excludes large bodies from ordinary automatic context but leaves discoverable compact cards with honest current/historical status. It need not be a second database. Tombstone retains only minimal historical address/type and unavailability, with its own schema branch; it need not satisfy all old full-record fields. Before deletion inspect reverse refs. Reject, retain a necessary excerpt, archive, or explicitly retire the dependent obligation with authority. Never leave a promised open verification with its sole grounds silently erased.

Logical deletion is not guaranteed physical erasure from all media/backups. For a removal request explain coverage through chat: current store, indexes, blobs, logs, exports, backups and Pi transcript can differ. Rebuild/invalidate stale derived indexes/skills. Deleting a body is not “deleted everywhere.” R1 retention is conservative: safe orphan staging cleanup and explicitly requested operations; semantic automatic retention belongs to a checked R2 policy. Deletion does not inflate success metrics or silently preserve claims of full historical coverage.
