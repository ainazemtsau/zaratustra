# Core v0.1 Stage 5, проход 1 — предметное продолжение

## Фактическая граница

Владелец утвердил первый проход `STAGE5-PLAN.md` на коммите
`e29bc0450ce4ee6c67e5e28859c8e410a82f1771`. Реализация расширяет
`zaratustra.foundation` и не устанавливает Pi RPC, DBOS или dispatcher.
Отдельного модельного процесса, модельного вызова и доступа к личным данным
в этом проходе нет. Исполнение Work проверяется синтетическими операциями.

Schema 4 устанавливается только явным `upgrade_continuation_space` после
schema 3. Обычное чтение или открытие старого пространства не повышает его
схему. Предыдущие миграции и точные ревизии не переписываются. `SpaceInfo` и
backup manifest различают версии 1–4; backup применяет SQLite Backup API к
одному предметному оригиналу. Интерактивный Stage 4 bridge и `read_execution`
поддерживают schema 3 и 4: существующие `StartAttemptRequest`, учёт вызовов,
публикация Artifact и отдельное принятие Work работают в обеих версиях.

## Публичный предметный контракт

| Операция / чтение | Фактическое действие |
|---|---|
| `AssignAttemptRequest` | Атомарно проверяет текущие Work, точные входы, ресурс, Grant, эпоху и предыдущее поколение; создаёт Attempt, назначение с закреплённой версией будущего исполнителя и один `launch` outbox. Это намерение, а не утверждение, что Pi RPC уже запущен. |
| `OpenWaitRequest` | Для текущего назначенного владельца сохраняет адресный вопрос, ожидаемого участника, точный остаток и ссылки на частичные Artifact. Повторный открытый вопрос той же Attempt запрещён. |
| `AnswerWaitRequest` | Требует действующих `work.write`, `record.read` и `receipt.read`, точной ревизии открытого ожидания, ожидаемого участника и актуальной Attempt. `receipt.read` нужен для точного повтора после потери подтверждения по действующим правилам чтения receipts. В одной предметной транзакции сохраняет ответ с источником полномочия, переводит назначение в `ready` и создаёт ровно один `resume` outbox. |
| `RequestAttemptStopRequest` / `RecordAttemptStopRequest` | Запрос остановки запрещает новые действия и отменяет ожидающие доставки. `unknown` сохраняет активную Attempt и удерживает ресурс; подтверждённый `stopped` закрывает открытый вопрос, прерывает Attempt и оставляет начатые модельные вызовы `unknown` с прежним резервом. Позднее подтверждение остановки может разрешить `unknown`. |
| `read_execution` / `read_receipt` | Возвращают текущие назначения, вопросы/ответы/остаток и outbox вместе с прежним снимком Work, ресурсов, Attempts и вызовов. Exact replay того же operation id возвращает квитанцию до текущих проверок; иной ответ на уже закрытое ожидание не создаёт продолжения. |

Записи назначения, ожидания и outbox являются типизированными таблицами Core,
не вложенным JSON в Work и не состоянием Pi-сессии. Вопрос, ответ, остаток и
причина остановки хранятся как управляемые bytes в SQLite; audit и receipts
содержат адреса и исходы без этих текстов. Outbox пока имеет только
`pending/cancelled`: доставки во внешний backend в проходе 1 нет.

Рабочий ресурс и поколение берутся из существующей Stage 4 Attempt. Перед
каждым новым контролируемым действием проверяются текущий Work/Artifact,
Grant, resource revision, epoch и generation. Назначение в `waiting`,
`stop_requested`, `unknown` или `stopped` не допускает новый модельный вызов
через существующую Stage 4 операцию. Права не выводятся из текста вопроса,
ответа или поля `actor` без локального `LocalAuthority`.

`WorkState.status` этого модельно-независимого прохода остаётся `proposed` до
отдельного `AcceptWorkRequest`: запись назначения или ответа не выдаётся за
фактическое выполнение. Полный переход Work через `ready/running/waiting`
из плана относится к проходу с настоящим исполнителем и наблюдаемым process
outcome. Это оставляет принятую семантику Stage 4 и точные прежние ревизии.

Принятие результата и подтверждение остановки назначенного исполнителя —
разные предметные действия. `AcceptWorkRequest` переводит Work в `succeeded`,
закрывает открытые ожидания и отменяет pending outbox. Назначение в `unknown`
остаётся `unknown`; назначение в `assigned/waiting/ready` переходит в
`stop_requested`. Активная назначенная Attempt продолжает удерживать
эксклюзивный ресурс без допуска новых эффектов, пока адресный
`RecordAttemptStopRequest(stopped)` не подтвердит остановку. Это подтверждение
разрешено и после принятия Work. Для интерактивной Attempt без долговечного
назначения сохраняется принятое поведение Stage 4: принятие прерывает Attempt.

## Обслуживание и восстановление

- Удаление Work стирает его назначения, вопросы/ответы/остатки и outbox,
  удаляет replayable receipts/fingerprints новых операций и использует уже
  существующую санацию закрытой live SQLite, managed Pi histories и
  затронутых backup packages.
- Удаление входного или адресованного частичного Artifact очищает зависимый
  текст вопроса/ответа/остатка и причины остановки, убирает их replayable
  intent, прерывает затронутую активную Attempt и отменяет outbox. Очистка
  `stop_reason` применяется также к назначениям со статусом `stopped` или
  `interrupted`, не переписывая уже известный исход. Адреса и разрешённая
  минимальная история остаются различимыми как `purged`/`interrupted`/`stopped`.
- Schema 4 backup содержит новые таблицы и точную эпоху. Restore идёт только
  в новое карантинное пространство, повышает эпоху и не выдаёт старые права.
  Свежий `RecoverRequest` прерывает старые Attempts/назначения, закрывает
  старые открытые вопросы и отменяет pending outbox. Сохранённый вопрос,
  ответ и остаток читаются после новой авторизации как история; старое
  продолжение не запускается автоматически.

Удаление управляемых копий не обещает очистки вручную скопированных файлов,
OS snapshots или внешнего provider retention. Этот проход не создаёт
`executor.sqlite3`, поэтому согласованный backup двух баз и санация DBOS
остаются критерием будущей реальной композиции.

## Воспроизведение и проверенный предел

`tests/zaratustra/foundation/test_continuation.py` создаёт только фиктивное
пространство. Один тест открывает вопрос, затем отдельный процесс Python
заново устанавливает локальную authority, читает сохранённый остаток и
отвечает. Родительский процесс проверяет одну квитанцию и один `resume`,
после чего проверяет дубль, неизвестную остановку и старое поколение.
Остальные тесты проверяют explicit upgrade и Stage 4 bridge, право повторного
чтения receipt, отзыв права, backup/quarantine/epoch и удаление Work/Artifact
вместе с управляемыми текстовыми копиями.

Последующие синтетические регрессии на базе `d04c87534a279e4e666075c8e663edf62dce4f47`
подтвердили исправление двух дефектов. После удаления зависимого Artifact
`stop_reason` отсутствует в API и закрытой live SQLite даже у завершённого
или прерванного назначения; соответствующий receipt недоступен, затронутый
managed backup удалён. При принятии Work после `unknown` конкурирующее
назначение до подтверждения `stopped` получает `resource_busy`; после
подтверждения ресурс доступен. Проверены также автоматический запрос остановки
при принятии активной назначенной Attempt и прежнее прерывание интерактивной
Attempt Stage 4. Команда focused feedback:

```powershell
$env:UV_CACHE_DIR = Join-Path (Get-Location) '_scratch\stage5-plan-uv-cache'
$env:ZARATUSTRA_SQLITE_DLL = Join-Path (Get-Location) '_scratch\stage4-interactive-20260923-a\sqlite\sqlite3.dll'
$env:PYTHONPATH = Join-Path (Get-Location) 'tools\sqlite_bootstrap'
uv run --locked python -m pytest tests/zaratustra/foundation/test_continuation.py -q
```

Это функциональная проверка Core, а не доказательство запуска/восстановления
Pi RPC или DBOS. Полная проверка delivery и её фактический результат записаны
отдельно в `RESULT.md`; focused run сам по себе не служит полным gate.
