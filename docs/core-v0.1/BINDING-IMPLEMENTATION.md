# Binding — пакет реализации Core v0.1

## Пользовательский путь

В обычном интерактивном Pi пользователь просит: «Передавай каждый принятый
`design` из Activity разработки в Activity планирования; предлагай его входом
`additional_design` открытому Work планирования» либо просит создать новый
Work по названной версии Method. Модель получает через `zara_binding` каталог
адресов и типизированный контракт операции, предлагает точную структуру;
пользователь подтверждает её в Pi. Core назначает реального actor/space из
локального host, проверяет право и структуру, создаёт версию в `trial`.
Отдельное подтверждённое действие переводит её в `enabled`. Команда
`/zara-binding` показывает версии и предложения. Принятие результата
производящего Work через штатный `/zara-accept` атомарно сохраняет срабатывание
и предложение/новый Work. Предложение пользователь адресно принимает или
отклоняет через тот же инструмент, указав основание.

Pi передаёт только намерение операции. Установленная foundation остаётся
единственным владельцем записи и квитанции. Назначенный Pi RPC не может менять
Binding. Каталог и JSON Schema приходят из фактических Pydantic контрактов;
Core не классифицирует пользовательский текст по ключевым словам и не запускает
семантического судью.

## Предметная запись

Схема 9 — явное аддитивное обновление схемы 8. Binding имеет id, непрерывные
версии, checksum определения и ревизии состояния `trial`/`enabled`/`paused`/
`retired`. Новая версия выводит старую из действия и получает только будущие
события принятия; прошлый результат допускается лишь отдельным `fire_binding`
с `backfill` и основанием. `trial` допускает адресную пробу без автоматической
подписки, `enabled` автоматически обрабатывает принятие. `paused` и `retired`
не создают новых действий. Существующие Work и открытые предложения сохраняют
свою судьбу отдельно от состояния Binding.

Источник — конкретная Activity, именованный выходной слот и media type.
Событие — принятая ревизия Work и операция принятия. Необязательное условие —
точная активная редакция Choice с именем/значением, относящаяся к исходной
Activity; смена редакции закрывает допуск. Отдельный текст Decision не считается
подтверждением содержания. Потребитель — новый составной Work в другой Activity
с точным MethodRef либо предложение входа открытому Work. Создание сопоставляет
выход с одним или несколькими входными слотами Method; дополнительные входы
Method закрепляются точными ArtifactRef. Предложение записывает свой слот и
ArtifactRef, не переписывая выполняющийся Work. Его принятие создаёт новую
ревизию Work; для составного Work — также ревизию действующего плана с новым
адресным основанием и проверкой сохранённых узлов. Входы Method, уже
закреплённые в Work, остаются закреплёнными; предложение составному Work
становится дополнительным именованным входом в истории Binding и основанием
плана. Активный Attempt ограждается существующим механизмом остановки новых
эффектов; неизвестный внешний исход не объявляется успехом.

При каждом исполнении Core заново проверяет текущие Grants/Decisions, источник,
точный Artifact, целевой Work/Activity, Method и предел причинной цепочки.
Повтор одного принятого события не создаёт второй Work/offer. Сохранены точные
версии, операции, ссылки, исходы `created`/`offered`/`blocked`/`stopped`, причины,
основания ручного backfill, решения по предложениям и ревизии входа.
Заблокированное срабатывание не откатывает принятие результата производителя.

Новые таблицы входят в существующую резервную копию и карантинное
восстановление. Удаление зависимого Work/Activity санирует определение и
квитанцию создания, прекращает новые срабатывания; удалённый Artifact делает
непринятое предложение недоступным. Используемая версия Method не удаляется
молча. Управляемые данные остаются в выбранном Core space, без второго
предметного хранилища в Pi/DBOS.

## Проверка и граница пакета

Адресные Core тесты проверяют версии, повтор, возобновление после нового
процесса, условия, текущие права, оба варианта потребителя, активный Attempt,
ревизию плана, backup/restore и удаление. Отдельный локальный probe проводит
каталог, контракт и две подтверждённые операции через обычный Pi и фиктивный
localhost provider; во втором процессе Pi выполняет `/zara-accept` и проверяет
срабатывание. Реальная модель и платный API
не используются. Качество смыслового выбора моделью устанавливается в
использовании, не выдаётся за детерминированный тест.

Источники/Claim, память и контекст — следующий функциональный пакет.
Pulse остаётся в выпускном пакете как небольшая вызываемая по требованию
структурная проверка без модели и изменения истории. Остальные согласованные
части первого Core не исключены завершением Binding.
