## Реализация

`read_execution` теперь даёт адресные решения текущей редакции плана и для
вложенного составного Work одновременно его привязку к плану предка и
собственный ближайший план. В `/zara-status` видны точные причины исхода,
изменённая предпосылка с удержанной/текущей ревизией, перепроверка,
применимость и Decision, waiver и Exception, версия Method, дети и ушедшие
узлы, переносы и закрепления. Назначенный Pi получает ту же структуру перед
prompt. Текст плана в эту проекцию не копируется; `/zara-work` не создаёт
интерактивную Attempt для составного Work.

DBOS launch теперь адресует очередь и версию приложения конкретной Attempt.
Без этого runner A мог восстановить ожидающий workflow B из общей версии и
проверить его в каталоге A. Новый workflow получает адресную пару.
Существующий workflow общей версии `zara-pi-rpc-dbos-3.0.0-v1` перед запуском
своего runner переводится публичным DBOS resume в очередь своей Attempt без
смены workflow ID, входов и версии. Runner слушает только эту очередь и
использует отдельный executor ID; чужие старые записи остаются в общей очереди
до их собственного запуска. Повторная доставка использует тот же устойчивый
workflow ID. Если ревизия плана отменяет launch до создания DBOS
workflow, поздний runner записывает наблюдаемую остановку без Pi и HTTP.
Действующие claim, recheck перед prompt и монитор Core каждые 0,5 с остаются
основным ограждением уже запущенного Pi.

## Живой probe

`tools.probe_stage6_pass3` создаёт только одноразовое schema 7 space, обычные
Pi 0.87.0 RPC и DBOS 3.0.0, локальный синтетический SSE provider. B ждёт
адресного ответа; конкурентный A исполняется в другом каталоге; третий Work
получает `resource_busy` на общем ресурсе. A принят, его отдельная
предпосылка исправлена и результат явно перепроверен. Редакция заменяет Art,
ограждает его назначенную Attempt без HTTP и переносит ожидающего B; после
адресного ответа B продолжает работу. Условное обязательство становится
`inactive` по точному Choice; Method v1 переходит в v2 с явными
сопоставлениями; одно действующее обязательство waived по Exception. Pi
исполняет G, затем Core принимает G → N → P. Отдельный обычный Pi читает
статус без модели. Новый процесс `python -I -X utf8` видит тот же итог.

Счёт HTTP по шагам успешного checkout-прогона: ожидание B — **1**, конфликт
ресурса — **1**, результат A — **2**, перепроверка — **2**, замена и ограждение
— **2**, ответ и результат B — **3**, Choice — **3**, результат G — **4**,
переход Method/принятие P — **4**, отдельный Pi/перезапуск/backup/restore —
**4**. Проверка `executor.sqlite3` и Pi homes не нашла маркеров плана,
оснований, исключения, вопроса и ответа. Backup format 2/schema 7 содержит
DBOS и Pi-файлы; restore изолирован в новой эпохе. Последовательное удаление
G, N, прежнего/нового Art, A, B, P и результатов Artifacts проверяет
`pending_jobs=0`, `live_store_sanitized=true`, отсутствие относящихся к
удалённым записям маркеров в live store и новом backup после каждого шага;
старый backup очищен.

Финальный отчёт успешной трассы:
`_scratch/probe-stage6-pass3-live-final/report.json`.
Это проверка синтетического транспорта, а не реальные модельные результаты.

## Исправление по независимому review `8130b1b`

Независимый Codex review точного
`8130b1ba2b2344284d523cf420a2327610aa133e` подтвердил исправление
прежних P1/P2, полный Windows gate (**678 тестов**), новую трассу (**4 HTTP**)
и установленный wheel того SHA (**3 HTTP**). Найдена отдельная регрессия:
адресный DBOS workflow, созданный предыдущим runner с executor ID `local`,
остаётся `PENDING` после падения до Core launch claim. Новый runner с executor
ID своей Attempt не видит его при startup recovery и ожидает результат
неограниченно. Это не объяснение иных наблюдений `database is locked` или
`rpc_transport`.

До правки внешний сценарий review точно повторён на чистом `8130b1b`:
прежний runner завершился кодом 90 до claim, workflow сохранил адресные
queue/app version, статус `PENDING` и executor `local`; новый runner за
ограниченные 15 секунд не создал вопрос и не отправил HTTP. Прежний runner
как контроль на тех же данных закончил SUCCESS с **2 HTTP**.

Исправление переводит только выбранный PENDING/local workflow адресной
версии через публичный `DBOSClient.resume_workflow` в очередь той же Attempt.
Workflow ID, входы, шаги и версия приложения сохраняются; процесс слушает
лишь адресную очередь и использует адресный executor ID. Это дополняет
прежний перенос записей общей очереди. Граница Core launch claim остаётся
решающей: до записанного claim восстановление выполняется один раз; после
claim повтор не запускает Pi/HTTP, даёт `process_outcome_unknown` и сохраняет
ресурс в состоянии unknown.

Живой межверсионный probe с настоящими DBOS/Pi подтвердил обе границы:
до claim — тот же ID, SUCCESS и **2 HTTP**, повторный запуск **0 HTTP**;
после claim — тот же ID, DBOS ERROR, Core assignment `unknown`, новых HTTP
**0**. Сохранённый fault probe текущего маршрута прошёл: до claim
восстановление, после claim unknown, потерянный HTTP-ответ без повторной
отправки. Старый сценарий двух соседних legacy workflows по-прежнему дал
A1/A2 `proposed`, A2 остался `ENQUEUED` после A1, всего **2 HTTP**. Новые

проверяют оба состояния claim и replay; **29** тестов затронутых файлов
