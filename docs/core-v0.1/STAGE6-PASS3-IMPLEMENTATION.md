## Реализация

`read_execution` теперь даёт адресные решения текущей редакции плана и для
вложенного составного Work одновременно его привязку к плану предка и
собственный ближайший план. В `/zara-status` видны точные причины исхода,
изменённая предпосылка с удержанной/текущей ревизией, перепроверка,
применимость и Decision, waiver и Exception, версия Method, дети и ушедшие
узлы, переносы и закрепления. Назначенный Pi получает ту же структуру перед
prompt. Текст плана в эту проекцию не копируется; `/zara-work` не создаёт
интерактивную Attempt для составного Work.

DBOS launch теперь адресует очередь и версию приложения конкретной Attempt.
Без этого runner A мог восстановить ожидающий workflow B из общей версии и
проверить его в каталоге A. Уже записанный workflow сохраняет свои прежние
адреса очереди и версии при повторной доставке и восстановлении; новый
получает адресную пару. Если ревизия плана отменяет launch до создания DBOS
workflow, поздний runner записывает наблюдаемую остановку без Pi и HTTP.
Действующие claim, recheck перед prompt и монитор Core каждые 0,5 с остаются
основным ограждением уже запущенного Pi.

## Живой probe

`tools.probe_stage6_pass3` создаёт только одноразовое schema 7 space, обычные
Pi 0.87.0 RPC и DBOS 3.0.0, локальный синтетический SSE provider. B ждёт
адресного ответа; конкурентный A исполняется в другом каталоге; третий Work
получает `resource_busy` на общем ресурсе. A принят, его отдельная
предпосылка исправлена и результат явно перепроверен. Редакция заменяет Art,
ограждает его назначенную Attempt без HTTP и переносит ожидающего B; после
адресного ответа B продолжает работу. Условное обязательство становится
`inactive` по точному Choice; Method v1 переходит в v2 с явными
сопоставлениями; одно действующее обязательство waived по Exception. Pi
исполняет G, затем Core принимает G → N → P. Отдельный обычный Pi читает
статус без модели. Новый процесс `python -I -X utf8` видит тот же итог.

Счёт HTTP по шагам успешного checkout-прогона: ожидание B — **1**, конфликт
ресурса — **1**, результат A — **2**, перепроверка — **2**, замена и ограждение
— **2**, ответ и результат B — **3**, Choice — **3**, результат G — **4**,
переход Method/принятие P — **4**, отдельный Pi/перезапуск/backup/restore —
**4**. Проверка `executor.sqlite3` и Pi homes не нашла маркеров плана,
оснований, исключения, вопроса и ответа. Backup format 2/schema 7 содержит
DBOS и Pi-файлы; restore изолирован в новой эпохе. Последовательное удаление
G, N, прежнего/нового Art, A, B, P и результатов Artifacts проверяет
`pending_jobs=0`, `live_store_sanitized=true`, отсутствие относящихся к
удалённым записям маркеров в live store и новом backup после каждого шага;
старый backup очищен.

Финальный отчёт успешной трассы:
`_scratch/probe-stage6-pass3-live-final/report.json`.
Это проверка синтетического транспорта, а не реальные модельные результаты.

## Проверки и ограничения

Адресные регрессии вложенной проекции и DBOS маршрута: 22 теста прошли.
Неизменённый Stage 5 probe прошёл с 2 HTTP. Неизменённый Stage 6 probe:
первый запуск упал с `storage: database is locked` при остановке через
`_record_stop`; второй обнаружил несовместимую строку нового Pi-статуса,
после сохранения прежнего фрагмента строки третий прошёл с 3 HTTP. Эти
исходы не доказывают устранение блокировки БД. Полный Windows gate и
установленный wheel точного чистого коммита фиксируются в `RESULT.md`
после выполнения.

Полный Windows `uv run --locked python -m tools.check --deliver` этого сеанса
прошёл: **676 тестов**, строгие типы, Ruff, **21** импортный контракт, sdist
и wheel. Это собственный прогон реализации, не независимый review.

`database is locked`, `rpc_transport` и расхождение `stale_basis` внутри
`any` остаются отдельными открытыми наблюдениями. Исполнение составного
родителя собственной Attempt, проход 4, реальные модели, миграция, PR и
приёмка не начаты.
