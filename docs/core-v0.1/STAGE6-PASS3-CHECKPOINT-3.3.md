## Контракт

### Выбор — вариант Decision

- `ChoiceState`: `variant: "choice"`, `statement`, `name`, `value`, область `scope` и
  `status` (`active`/`revoked`). Имя и значение — структурные идентификаторы
  `^[a-z][a-z0-9_-]*$`, не длиннее 80 символов. Область `DecisionScope` — ровно один Work
  или одна Activity (`kind`, `record_id`).
- Выбор создаётся, пересматривается и отзывается прежними `CreateDecisionRequest` и
  `ReviseDecisionRequest` по праву `decision.write`. Поле `state` этих запросов принимает
  правило (`DecisionState`) или выбор; различает их только `variant`. У правила этого поля
  нет, поэтому канонический JSON, fingerprint и хранимое тело существующих Decision не
  меняются.
- При создании область должна существовать с этим видом и не быть удалённой (`not_found`,
  `content_unavailable`).
- Ревизия сохраняет вариант: правило не становится выбором (это молча сняло бы правило
  доступа), выбор не становится правилом — `invalid_request`. Выбор сохраняет имя и
  область — `invalid_request`; для другой области создаётся другой выбор. Значение,
  формулировка и статус меняются ревизией; отзыв — ревизия со статусом `revoked`.
- Проверка доступа учитывает только правила `require_grant`/`deny`: `_authorize` пропускает
  выборы, в `decision_refs` audit попадают только правила.
- Ниже schema 7 любой выбор отказывает `unsupported_schema`, ничего не записано.
- `read_decision(path, decision_id, authority, revision=None)` читает текущую или точную
  ревизию правила или выбора по праву `record.read`; отсутствующая ревизия — `not_found`,
  перехода к latest нет.

### Условная применимость обязательства

- `MethodObligation.applicability` — прежнее `"always"` или `ChoiceApplicability`:
  `{kind: "choice", choice: имя, active: значения, inactive: значения}`. Значения
  уникальны, их хотя бы одно, списки не пересекаются. Иное, как и неподдержанный вид, —
  ошибка проверки схемы.
- Версия Method с условным обязательством ниже schema 7 отказывает `unsupported_schema`.
- Материализация: безусловное обязательство — `active/open`, как прежде, с прежними
  байтами полезной нагрузки; условное — `unresolved/open`.
- `ObligationRevision`: применимость (`active`/`inactive`/`unresolved`) и исполнение
  (`open`/`satisfied`) — отдельные поля. Новое поле `choice` — адрес Decision, решившего
  применимость; пока оно пусто, его нет в JSON. `basis` — текст операции, записавшей эту
  ревизию (решения применимости или подтверждения). Схема не допускает несогласованных
  сочетаний:
  - безусловное обязательство всегда `active` и без адреса выбора;
  - условное `unresolved` ровно тогда, когда адреса выбора нет;
  - не-`active` экземпляр всегда `open` и без доказательства.

### Применимые выборы и формальный конфликт

- Области, охватывающие Work W: сам W, каждый составной Work над ним (обход
  `work_plan_children`; вложенность появится в 3.9) и Activity W.
- Применимые к W выборы с именем n — текущие действующие выборы с этим именем, область
  которых охватывает W.
- Если их значения различаются, это формальный конфликт: `decision_conflict` с адресами
  всех применимых выборов этого имени (по порядку id Decision). Старшинства по области,
  конкретности или времени нет. Записанная ревизия экземпляра не переписывается. Конфликт
  снимается только пересмотром или отзывом выбора.

### Лист `decision_value`

- `PlanCondition(kind="decision_value", decision_id, decision_revision, name, value)`. Поля
  `name` и `value` отсутствуют в каноническом JSON прочих листов, поэтому fingerprint
  прежних планов не меняются. Неверная форма — ошибка проверки схемы.
- План с таким листом создаётся и редактируется только в schema 7 (иначе
  `unsupported_schema`). Точная ревизия должна существовать и быть выбором с этим именем,
  иначе `invalid_plan`; ничего не записано.
- Лист вычисляется для Work, чьё это условие: готовность ребёнка — для ребёнка, условие
  завершения — для родителя. Порядок:
  1. значение точной ревизии другое — `dependency_closed`: лист уже не станет истинным;
  2. точная ревизия не текущая или не действует — `stale_basis`;
  3. применимые к Work выборы этого имени вместе с выбором листа расходятся —
     `decision_conflict` со всеми адресами.
- Лист служит условием готовности, завершения и выбора ветки. Он перепроверяется при
  выдаче узла, перед каждым эффектом назначенного ребёнка (gate прохода 2) и при принятии
  родителя (условие завершения).
- Как и `decision_active`, лист — точная предпосылка своего Work: после пересмотра или
  отзыва его Decision `close_work` с исходом `stale` может его назвать.

### Операция `resolve_obligation_applicability`

`ResolveObligationApplicabilityRequest`: `work_id` родителя, `key`,
`expected_plan_revision`, `expected_obligation_revision`, точная ссылка `choice`,
`basis`. Права — `work.write` на родителе (действие операции) и действующий `method.use`
в Activity родителя. Проверки в порядке исполнения; каждый отказ ничего не записывает:

| Проверка | Отказ |
|---|---|
| schema 7 | `unsupported_schema` |
| текущие права | `permission_denied`, `decision_denied` |
| ожидаемая ревизия плана | `stale_plan` |
| основание плана и входы родителя актуальны | `stale_basis` |
| ключ объявлен Method | `not_found` |
| ожидаемая ревизия обязательства | `stale_obligation` |
| родитель не закрыт | `work_closed` |
| обязательство условное | `unconditional_obligation` |
| действующего решения нет: экземпляр `unresolved` или его выбор уже не текущий и не действует | `applicability_resolved` |
| точная ревизия Decision существует | `not_found` |
| это выбор | `choice_required` |
| имя выбора — имя из условия | `choice_mismatch` |
| ревизия текущая и действует | `stale_basis` |
| область охватывает родителя | `choice_mismatch` |
| значение перечислено в условии | `choice_mismatch` |
| среди применимых выборов этого имени нет другого значения | `decision_conflict` |

Результат — новая ревизия экземпляра: `active/open` или `inactive` (исполнение `open`,
без доказательства), с адресом выбора и текстом основания. Квитанция содержит Work, ключ,
ревизию, применимость и адрес выбора, но не текст основания. Цели audit — родитель на
ревизии плана и точная ревизия Decision. Точный повтор возвращает прежнюю квитанцию.

Каждое новое решение начинает исполнение с `open`, как в плане: «active/open». Если
обязательство было подтверждено при решении, выбор которого затем пересмотрели, после
нового решения его нужно подтвердить снова.

### Перепроверки зависимых операций

Множество применимых выборов вычисляется заново в транзакции каждой операции.

| Операция | Перепроверка |
|---|---|
| Выдача узла; каждый эффект назначенного ребёнка | лист `decision_value` его готовности: `dependency_closed`, `stale_basis`, `decision_conflict` |
| Подтверждение обязательства | сначала состояние экземпляра: `obligation_unresolved`, `obligation_inactive`, устаревшее решение — `stale_basis`; затем конфликт — `decision_conflict` |
| Связь выхода родителя | конфликт у каждого решённого условного обязательства — `decision_conflict`; нерешённые не мешают независимой работе |
| Принятие родителя | порядок ниже |

Принятие родителя отказывает в таком порядке:

1. конфликт у любого условного обязательства, решённого или нет, — `decision_conflict`;
2. решение, чей выбор уже не текущий или не действует, — `stale_basis`;
3. активное невыполненное обязательство закрытой ветви — `dependency_closed` (3.2);
4. нерешённое обязательство — `obligation_unresolved`;
5. активное невыполненное — `obligation_open`;
6. далее прежние проверки: выходы, условие завершения (в том числе листы
   `decision_value` родителя) и точные доказательства — только у активных обязательств.

Неактивному обязательству с действующим выбором результат не нужен.

### Производное состояние

- `ObligationProgress.applicability`: `active`, `inactive`, `unresolved` или производное
  `applicability_stale`. Последнее означает записанное решение, чей выбор уже не текущий
  или не действует. `choice` — записанный адрес.
- Конфликт у условного обязательства — блокирующие причины `decision_conflict` с ключом,
  именем и адресом каждого Decision. Родитель `blocked`, как при устаревшей предпосылке:
  до фаз, но с адресами активных ветвей и `branch_review`.
- Следующие шаги (`ready`):
  - `applicability_pending` — ключ, имя и адрес родителя, если обязательство
    `unresolved` и конфликта нет;
  - `applicability_stale` — ключ, имя и адрес устаревшего выбора;
  - `confirmation_pending` — только у активных открытых обязательств.
- `acceptance_pending` — если каждое объявленное обязательство активно и выполнено или
  действующе неактивно и выполняются правила принятия.
- У действующе неактивного обязательства выход роли не входит в предпосылки родителя, и
  ради него закрытая ветвь не попадает в `branch_review`.
- Ребёнок с листом `decision_value` читается `blocked`:
  - `dependency_closed` или `stale_basis` — с адресом Decision листа и именем;
  - `decision_conflict` — с каждым адресом и именем.
- `StatusReason` получил необязательные `key` и `name`. Пока они пусты, их нет в JSON,
  поэтому прежние причины читаются как раньше.

## Изменения принятого поведения

Для данных, которые могли существовать до 3.3 (без выборов, только безусловные
обязательства), поведение прежнее: каждое безусловное обязательство читается `active`, и
новые проверки его не затрагивают. Тесты проходов 1–2 и 3.1–3.2 не менялись и проходят;
закреплённые константы прохода 2 (fingerprint запросов и checksum Method) совпадают.

Видимое для прежних данных отличие одно: `_authorize` и `ReviseDecisionRequest` читают тело
Decision через объединение «правило или выбор». Повреждённое хранимое тело теперь
отказывает `corrupt_space`, а не необработанной ошибкой проверки. Ревизия правила в
правило не меняется.

## Обслуживание данных

- **Выборы** — обычные ревизии Decision в `records`/`record_revisions`:
  - точное чтение — `read_decision`;
  - тот же SQLite-снимок Core при backup;
  - карантинный restore их сохраняет. После recover они продолжают действовать: Decision,
    в отличие от Grant, не привязан к эпохе.
- **Удаления Decision нет** со Stage 2, и этот предел сохраняется. Выбор не удаляется,
  только отзывается. Удаление Work не удаляет выборы с его областью: после удаления
  детей и самого Work они ничего не охватывают.
- **Ревизии применимости** — ревизии обязательств родителя: точное чтение
  `read_obligation(revision=…)`, backup/restore, удаление вместе с родителем и выводом их
  квитанций из повтора, как в проходе 1.
- **Удаление зависимости роли** (ребёнка или Artifact). Действующая санация прохода 1
  считает основание решения скопированным основанием:
  - ревизия с ним заменяется маркером недоступности, квитанция выводится из повтора
    (`history_unavailable`);
  - последней становится ревизия с той же применимостью и тем же адресом выбора, но без
    основания;
  - маркер основания отсутствует в live SQLite после `complete_deletions`, старый пакет
    backup удалён.

  Полное правило 3.3–3.4 для удаления зависимости и его проверка относятся к 3.4.
- Тексты формулировки выбора и основания решения не попадают в закрепления, outbox, вход
  DBOS workflow и снимок исполнения. Снимок несёт только ключи, состояния и адреса.

Проверка чувствительности тестов. Каждая из восьми намеренных поломок, внесённых
временно, валит хотя бы один из этих тестов:

- подтверждение без проверки применимости;
- связь выхода без перепроверки решённых обязательств;
- область Activity, которая ничего не охватывает;
- выбор Work, который скрывает выбор Activity;
- решение, которое не устаревает;
- лист, который не закрывается при другом значении;
- принятие без проверки `unresolved`;
- состояние без `applicability_pending`.
