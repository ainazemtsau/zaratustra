Владелец закрыл техническое review частей 3.6–3.7 на
`98a61f20bf0eec06fa3e9e1501b35f0bb31b6ecc` и разрешил часть 3.8 по

Этот пакет реализует только переход начатого составного Work на точную следующую

перенос или ограждение Attempt и обслуживание данных. Часть 3.9, приёмка schema 7,

Наблюдение `database is locked` остаётся открытым без установленной причины;
этот пакет не заявляет его устранение.

## Контракт перехода

- Публикация Method v2 не меняет начатый Work, его v1-обязательства и закрепления.
  Только `revise_active_plan` с `target_method` (id, version, checksum) и
  `obligation_mapping` переводит родителя и план N+1 на v2 атомарно.
- Цель должна быть более новой версией того же Method с теми же именованными
  входами и выходами. Проверяются `method.use` для v2, текущие права, решения
  по узлам и совместимость пары роль/слот/тип каждого `carry`. Каждый действующий
  ключ v1 требует ровно одного `carry` или `retire`; `retire` требует адресного
  Exception Decision именно для старого требования.
- Старый ключ получает явную снятую ревизию. При повторном использовании имени
  ключа новая версия получает следующую ревизию после снятия. Новые ключи v2
  материализуются в той же транзакции. Исторические снятые ключи не входят в
  сопоставление следующего перехода.
- Выполненное обязательство переносится только если в новом плане тот же
  ребёнок имеет актуальный принятый результат с тем же точным Artifact и
  действующими предпосылками; иначе новый экземпляр открыт. Применимость
  переносится только при том же условии, waiver — только если адресный Exception
  разрешает новый ключ и v2. Копия основания хранит адрес исходной ревизии для
  санации при последующем удалении её зависимости.
- Действующая Attempt сохраняемого узла переносится под v2 после проверки
  прежнего закрепления и повторного допуска узла. Attempt другого узла
  ограждается. Старое закрепление и переносы остаются в истории с исходной
  версией Method. Пока активная либо `unknown` Attempt ссылается на v1,
  удаление v1 отказывает `method_in_use`.

## Адреса и обслуживание

Schema 7 дополнена `work_plan_methods` для точной версии Method каждой редакции
плана и `work_obligation_transitions` для адресов источников, преемников и
Exception Decisions. При явном upgrade из schema 6 все прежние редакции
закрепляются за текущим тогда Method: до schema 7 переход версии не существовал.
SHA-256 полного набора DDL schema 7 на этой контрольной точке —
`3EC8A66BCBB67DF8C41CC9859B6A591BE5C974F38071988F1E23D8232F63A79F`.
По решению владельца DDL schema 7 дополняется по частям до выпуска прохода;
пространства прежних контрольных точек одноразовые и не мигрируют молча.
`read_plan_method` и `read_method_transition` читают точную историю через
публичный Core. Удаление старого определения Method убирает его содержимое и
квитанцию публикации, но оставляет адреса исторических редакций; точное чтение
определения даёт `content_unavailable`. Удаление родительского Work убирает оба
новых набора строк. Управляемые backup сохраняют историю до удаления и
загрязняются при удалении Method или зависимого Artifact; новый backup строится
из очищенного live store.

## Проверенные сценарии

`tests/zaratustra/foundation/test_method_transition.py` проверяет через
публичный Core:

1. публикация v2 без действия на v1, переход с `carry` и `retire`, новый ключ,
   replay и точные чтения v1/v2;
2. отказы `obligation_unmapped`, `exception_required`, `method_incompatible`,
   `stale_plan` и `stale_work` без частичной записи;
3. последовательный переход v1→v2→v3 только по действующим ключам;
4. перенос действующей Attempt сохранённого ребёнка под v2, ограждение
   заменённого и отказ поздним эффектам v1;
5. отказ удалить v1 при активном и `unknown` закреплении Attempt;
6. открытие нового требования после замены ребёнка и `evidence_mismatch`
   для старого Artifact при независимом результате нового ребёнка;
7. перенос выбора только при том же условии применимости и waiver только
   в пределах точного Exception;
8. санацию скопированного основания после удаления Artifact: старый backup,
   live SQLite, новый backup, новое чтение и новый процесс;
9. удаление v1 после завершения его зависимостей, точную адресную историю,
   backup/restore и чтение новым процессом;
10. удаление родителя после последовательных переходов и очистку обеих новых
    таблиц из закрытой SQLite.

Локальный Windows `uv run --locked python -m tools.check --deliver`: PASS,
656 тестов, Ruff format/check, mypy для 184 файлов, 21 импортный контракт,
sdist и wheel. Последний полный прогон выполнен после добавления проверки
очистки родителя; точная атрибуция повторена в `RESULT.md`. Эти проверки
являются инженерным свидетельством, не приёмкой.
