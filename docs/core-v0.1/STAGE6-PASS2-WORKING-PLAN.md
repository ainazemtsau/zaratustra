# Stage 6, проход 2 — рабочий план

Основание: приёмка прохода 1 на `29d887d41f1639dc6ddb354a2039603cb1a30d94`
(`STAGE6-PASS1-ACCEPTANCE.md`) и разрешение владельца только на проход 2
`STAGE6-PLAN.md` от 2026-09-24.

1. Явная аддитивная schema 6: у назначенной дочерней Attempt адресное
   закрепление плана — родитель, роль, ревизия плана, точные id/версия/checksum
   Method. Upgrade только отдельной операцией; schema 4/5 и путь
   `method="none"` не меняются.
2. Общий gate `apply_operation`: назначение дочернего Work и каждое следующее
   действие его Attempt (launch claim, вопрос, ответ, prepare/admit/send,
   публикация) заново проверяют текущий план, выдачу, зависимости, точные
   входы, `method.use` и закрепление Attempt. Запрос и запись остановки и
   исхода вызова остаются доступными. Родительский Work и интерактивная
   Stage 4 Attempt составного Work по-прежнему отказывают. Outbox и DBOS
   несут только адреса.
3. Состояния `proposed/ready/running/waiting/blocked/succeeded` выводятся из
   тех же записей Core (выдача, готовность, назначение, ожидание, остановка,
   `unknown`, результат), а не хранятся вторым полем. Их показывают
   `read_execution`, отдельное чтение и интерактивный Pi.
4. Pi-адаптер: назначенный Pi RPC и интерактивный bridge работают на
   schema 5/6. Предметный отказ до запуска закрывает назначение без процесса
   Pi и без HTTP; принятие результата остаётся отдельной операцией.
5. Обслуживание: закрепления, DBOS workflows и Pi RPC homes дочерних Attempt
   сразу входят в backup, карантинный restore, удаление и последовательную
   санацию.
6. Проверка: модельно-независимые регрессии; localhost probe через обычный
   Pi RPC (вопрос/ответ, публикация, отдельное принятие, разблокировка
   следующего узла, дубли, ноль HTTP при отказе, reopen, интерактивный Pi);
   установленный wheel вне checkout; `tools.check --deliver`; документы,
   `RESULT.md` и локальный коммит. Реальная модель, миграция разработки и
   проходы 3–4 не начинаются.
