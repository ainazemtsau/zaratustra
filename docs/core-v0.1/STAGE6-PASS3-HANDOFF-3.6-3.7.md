### Окружение Linux (эфемерное; в новом контейнере его нужно собрать заново)

- Foundation при импорте требует SQLite ровно 3.53.3 (`zaratustra/foundation/runtime.py`).
  `.venv` проекта (uv, CPython 3.13.7) содержит SQLite 3.50.4. Поэтому тесты и probe через
  `uv run` на Linux не импортируют foundation. `uv run` годится для ruff, mypy,
  lint-imports и `uv build`.
- В этой сессии пакеты conda-forge `python-3.13.7-h2b335a9_100_cp313`,
  `libsqlite-3.53.3-h0c1763c_0`, `openssl-3.5.8-h781a0a9_0` и
  `libmpdec-4.0.0-hb03c661_2` были распакованы в префикс вне репозитория. Из него создан
  venv, проект установлен editable с зависимостями из `uv.lock`, и `bin` этого venv стоял
  первым в `PATH`. Это же нужно для `lint-imports` в `tests/tools/test_check.py`.
  Префикс и venv лежали во временном каталоге сессии и потеряны.
- Pi 0.87.0: `npm` в `_scratch/stage6-pass3-pi-runtime` с зависимостями
  `@earendil-works/pi-coding-agent` и `@earendil-works/pi-ai` 0.87.0. В контейнере были Node
  v22.22.2 и npm 10.9.7. Это окружение, не продукт.
- Хук `.githooks/pre-commit` вызывает `#!/usr/bin/env python`. В контейнере это системный
  Python 3.11, поэтому коммитить с Python 3.13 (SQLite 3.53.3) первым в `PATH`.

Решения пакета 3.6–3.7, которые нужно сохранить (подробно — раздел «Толкования»
документа пакета):

- Операция `revise_active_plan`, модуль `zaratustra.foundation.active_plan`. Решения
  `keep`, `replace`, `cancel`, `stale`, `release` и `add` записываются адресами в
  `work_plan_nodes`.
- Строка schema 5 `work_plan_children` не переписывается. Новые члены роли хранятся в
  `work_plan_members`.
- Фактическая выдача — ревизия выдачи или последняя ревизия, куда её перенёс `keep` после
  перепроверки (`child_binding`).
- Роль, покинувшую план, снова заполняет только `add` с новым Work. `ReviseWorkPlanRequest`
  такую роль не заполняет.
- Выполненное обязательство, чьё доказательство принадлежит ушедшему из роли Work, получает
  новую ревизию `open` с `reopened = node_replaced`.
- Attempt сохранённого узла продолжает работу через `execution_plan_transfers`; её
  закрепление не переписывается. Прочие Attempt в schema 7 огорожены: `stale_plan` раньше
  `work_closed`, поздний ответ на закрытое ожидание — `stale_wait`. Остановка и исход
  отправленного вызова доступны.
- Индекс санированного плана в schema 7 содержит `role_works`. Схемы 5–6 сохраняют прежние
  байты. Семена и зависимости удаления идут по тому Work, который заполнял роль в данной
  ревизии.
- Новые необязательные поля моделей имеют `exclude_if`, поэтому прежний канонический JSON
  не меняется.
- Пространства schema 7 прежних контрольных точек отказывают `unsupported_schema`.
  Текущий SHA-256 DDL schema 7 —
  `E9F28ECE8C5D6A5AEF297247029572DFC5750B7854950063AB40E8F88FF1744B`.

Ориентиры по коду для P1/P2. Это не текст отзыва и не воспроизведение: только факты о
коде `3c18172`, чтобы быстрее найти место. Шаги и ожидаемое поведение брать из полного
отзыва.

- `sanitize_deleted_dependency` (`composition.py`) санирует ревизию плана, только если в
  её содержимом удаляемый Work есть среди `children` или удаляемый Artifact есть среди
  ссылок. Решения `work_plan_nodes` при этом не читаются: `replaced_work_id` у `replace` и
  `work_id` у уходящих `cancel`/`stale`/`release`. `rationale` ревизии N+1 лежит в её
  содержимом.
- Две ветви этого кода остались ролевыми, а не по Work, и в 3.6 к истории ролей не
  приводились:
  - при удалении Artifact ревизия обязательства с этим доказательством сеет свою роль;
    дальше зависимыми становятся все ревизии обязательств (с доказательством или
    основанием) этой роли и ролей, зависящих от неё по рёбрам текущего плана;
  - в `_outcome_dependencies` (ей пользуются основания исходов и перепроверок)
