## Контракт

- `ReviseActivePlanRequest` принимает `nested_plan` только для нового
  составного узла в `add` или `replace`. Его Work, план ревизии 1, простые
  дети, экземпляры обязательств и новая редакция плана родителя записываются
  одной транзакцией. Старый `CreateCompositeWorkRequest` не создаёт вложенные
  узлы напрямую. Схема остаётся 7; новые поля отсутствуют в канонических
  запросах прежних сценариев.
- `role_methods` закрепляет точную версию Method для заполненной роли. Если
  роль не объявлена, выбранный `MethodRef` фиксируется в `PlanChild.state`
  новой редакции до выдачи. Для выбранного Method требуются `method.use`,
  совпадающие входы и выходы; неподдержанные capabilities отказывают
  `unsupported_condition`.
- Выдача внука, его назначение и эффекты, подтверждения и редакции вложенного
  Work проверяют действующую связь на каждом уровне, состояние предков и
  `method.use`. Собственная Attempt составного узла отказывает
  `unsupported_composite_execution`. Принятие вложенного Work проверяет его
  собственный план и обязательства вместе с членством в плане родителя;
  родитель использует принятый выход узла. Производный статус проходит по
  вложенным детям без второго сохранённого статуса.
- `replace`, `cancel` и `stale` вложенного узла требуют адресного
  `descendants`: каждый незавершённый потомок, роль, непосредственный
  родитель, ожидаемая редакция его плана, собственная ревизия Work и исход.
  Лишний потомок даёт `mapping_invalid`, пропущенный — `open_children` с
  адресом, устаревшие ревизии — `stale_plan`/`stale_work`. Для каждого исхода
  проверяются `work.accept`, Method предков и предпосылки `stale`. Потомки
  закрываются снизу вверх через обычный путь 3.1; любой отказ откатывает
  всю редакцию. Завершённые потомки сохраняют прежний исход.
- Удаление внука проходит через сохранённые адреса членства к историческим
  планам предков, основаниям исходов и подтверждениям. Поэтому текст
  зависимой редакции корня и основания может очищаться при удалении G, а
  независимая новая роль сохраняется. План/обязательства самого вложенного
  Work живут под его ключом и удаляются после его детей.

## Проверка

`tests/zaratustra/foundation/test_nested_composition.py` проверяет публичным
Core точную привязку N@2 после публикации N@3, отказ N@3, материализацию
обязательства, отказ выдать G до N, выдачу G после N, принятие G→N→корень,
статус корня при исполняющемся G, отказ собственной Attempt составного узла
через общий gate, обязательное перечисление потомков, отказы из-за
устаревших ревизий, лишнего адреса и отсутствия `work.accept`, а также
атомарное закрытие. При открытом вопросе и отправленном вызове закрытие
ставит Attempt в `stop_requested`, закрывает вопрос и отмечает вызов
`unknown`; поздний ответ и эффект отказывают, резерв остаётся и новая ветвь
на том же корне получает `resource_busy`, пока независимый узел выдаётся.
После принятия проверены backup, удаление G→N→корень, очистка маркера
из закрытой SQLite и нового backup, чтение новым процессом.

Полный локальный Windows `uv run --locked python -m tools.check --deliver`:
PASS, 662 теста, Ruff format/check, mypy для 186 файлов, 21 импортный
контракт, sdist и wheel. Перед итоговым прогоном один полный запуск обнаружил
регрессию `revalidate_result`: новая проверка собственного Work ошибочно
отказывала при изменившейся предпосылке, которую операция как раз должна
перепроверять. Проверка ограничена предками; прежние сценарии 3.5 и 3.6–3.7
повторены целевым Windows-прогоном. Отдельный повтор полного gate выполнен на
окончательном дереве.

## Исправление открытого P1 после независимого review

Codex независимо воспроизвёл на `74485ca` пропуск зависимости: X был только
входом G в дереве P → N → G; после принятия G/Y, N и P с основанием, цитирующим X,
удаление X очищало основание N, но оставляло основание P, replay, квитанцию,
маркер в закрытой SQLite и новом backup. `pending_jobs=0` и
`live_store_sanitized=true` не означали, что копия удалена. На неизменённом коде
`f336fab` этот же публичный сценарий повторён перед правкой.

`_outcome_dependencies` теперь собирает адреса Artifact по всему сохранённому
дереву членов: редакции Work, планы вложенных составных Work и их доказательства.
Индекс санированного плана удерживает зависимости каждого точного заполнителя роли,
включая неизвестный старый индекс; удаление проверяет его после перезапуска.
Основания исходов и перепроверок проходят вверх по точным связям с предками.
Новая ветвь роли не наследует зависимости заменённой ветви.
Текст редакции плана проверяется по её собственным ссылкам и вложенным планам,
уже записанным на момент этой редакции: результат или подтверждение ребёнка,
появившиеся позднее, не делают прежний план недоступным. Это сохраняет прежние
сценарии 3.6–3.8 при удалении старого доказательства.

Новые регрессии `test_nested_deletion.py` проходят через публичный Core: полный
цикл G → N → P при X во входе G и отдельно в basis плана N, подтверждение P,
закрытие P, перепроверку результата G, исторический план N до выдачи G,
последовательные удаления с новым процессом, backup и карантинный restore,
а также независимые принятие, подтверждение, квитанции и replay замещающей
и соседней ветвей. Результаты итогового Windows gate и интеграционных probes записаны
в `STAGE6-PASS3-REVIEW-3.9-OPEN.md` как проверки сеанса исправления,
отдельно от исходных 662 тестов сеанса реализации и независимого review.

## Продолжение после независимого review `63f64eb`

Независимый Codex review точного коммита
`63f64ebce37502028eca93a77db6c8458d1d5add` подтвердил устранение
предыдущего P1 санации и сам выполнил полный Windows `tools.check --deliver`:
PASS, 669 тестов, mypy для 187 файлов, Ruff, 21 импортный контракт, sdist и
wheel. Review остаётся открытым: отдельные публичные сценарии нашли три
новых дефекта. Его точные шаги и результаты приведены в
`STAGE6-PASS3-REVIEW-3.9-OPEN.md`; этот результат проверки нельзя
приписывать сеансу исправления.

До правки все три сценария повторены на исходном `63f64eb`, в том числе
закрытие дерева с исполняющимся S. После правки `AcceptWorkRequest` вложенного
составного Work проходит общий `check_child_plan` всей цепочки предков до
собственного `check_parent_acceptance`. Изменившийся обязательный вход P
поэтому атомарно отказывает `stale_basis` при попытке принять N; прежняя
перепроверка собственных предпосылок остаётся отдельным путём.

При закрытии уходящего дерева обход проходит через уже принятый составной
Work и находит каждого ещё открытого потомка. Пропущенный S отказывает
`open_children`; адресно указанный S закрывается обычным путём, включая
`stop_requested`, закрытие outbox и перевод отправленного вызова в `unknown`
с сохранённым резервом. Успешные H и L сохраняют результат и replay.
Разрешение закрыть потомка под принятым предком ограничено этим атомарным
обходом; прямой `close_work` по-прежнему отказывает `work_closed`. Принятие H
с открытым необязательным S остаётся допустимым.

При создании вложенного составного Work каждый именованный вход проверяется
на `media_type` закреплённой версии Method. Оба пути `add` и `replace`
атомарно отказывают `output_mismatch` для неверного типа и принимают
совпадающий тип. Содержимое JSON как формат здесь отдельно не проверяется.

Пять новых публичных регрессионных вариантов в
`test_nested_composition.py` проверяют отказ принятия N после изменения
входа P и чтение новым процессом; отсутствие требования завершать
необязательный S для принятия H; обязательное закрытие S при замене N,
включая действующую Attempt; сохранение H/L и независимой ветви; тип
именованного входа при `add` и `replace`, включая успешный случай.
Прежние тесты вложенной санации, независимых ветвей и цикл G → N → P сохранены.
Финальные проверки сеанса исправления фиксируются отдельно в открытом review.
Полный Windows `uv run --locked python -m tools.check --deliver` на исправленном
пакете прошёл: 674 теста, mypy для 187 файлов, Ruff, 21 импортный контракт,
sdist и wheel. Checkout Stage 6 и Stage 5 RPC probes прошли соответственно с
3 и 2 синтетическими HTTP; установленный wheel прошёл вне checkout с 3
синтетическими HTTP. `database is locked` и `rpc_transport` остаются
отдельными открытыми наблюдениями без заявленного устранения.
