## Контракт

- `ReviseActivePlanRequest` принимает `nested_plan` только для нового
  составного узла в `add` или `replace`. Его Work, план ревизии 1, простые
  дети, экземпляры обязательств и новая редакция плана родителя записываются
  одной транзакцией. Старый `CreateCompositeWorkRequest` не создаёт вложенные
  узлы напрямую. Схема остаётся 7; новые поля отсутствуют в канонических
  запросах прежних сценариев.
- `role_methods` закрепляет точную версию Method для заполненной роли. Если
  роль не объявлена, выбранный `MethodRef` фиксируется в `PlanChild.state`
  новой редакции до выдачи. Для выбранного Method требуются `method.use`,
  совпадающие входы и выходы; неподдержанные capabilities отказывают
  `unsupported_condition`.
- Выдача внука, его назначение и эффекты, подтверждения и редакции вложенного
  Work проверяют действующую связь на каждом уровне, состояние предков и
  `method.use`. Собственная Attempt составного узла отказывает
  `unsupported_composite_execution`. Принятие вложенного Work проверяет его
  собственный план и обязательства вместе с членством в плане родителя;
  родитель использует принятый выход узла. Производный статус проходит по
  вложенным детям без второго сохранённого статуса.
- `replace`, `cancel` и `stale` вложенного узла требуют адресного
  `descendants`: каждый незавершённый потомок, роль, непосредственный
  родитель, ожидаемая редакция его плана, собственная ревизия Work и исход.
  Лишний потомок даёт `mapping_invalid`, пропущенный — `open_children` с
  адресом, устаревшие ревизии — `stale_plan`/`stale_work`. Для каждого исхода
  проверяются `work.accept`, Method предков и предпосылки `stale`. Потомки
  закрываются снизу вверх через обычный путь 3.1; любой отказ откатывает
  всю редакцию. Завершённые потомки сохраняют прежний исход.
- Удаление внука проходит через сохранённые адреса членства к историческим
  планам предков, основаниям исходов и подтверждениям. Поэтому текст
  зависимой редакции корня и основания может очищаться при удалении G, а
  независимая новая роль сохраняется. План/обязательства самого вложенного
  Work живут под его ключом и удаляются после его детей.

## Проверка

`tests/zaratustra/foundation/test_nested_composition.py` проверяет публичным
Core точную привязку N@2 после публикации N@3, отказ N@3, материализацию
обязательства, отказ выдать G до N, выдачу G после N, принятие G→N→корень,
статус корня при исполняющемся G, отказ собственной Attempt составного узла
через общий gate, обязательное перечисление потомков, отказы из-за
устаревших ревизий, лишнего адреса и отсутствия `work.accept`, а также
атомарное закрытие. При открытом вопросе и отправленном вызове закрытие
ставит Attempt в `stop_requested`, закрывает вопрос и отмечает вызов
`unknown`; поздний ответ и эффект отказывают, резерв остаётся и новая ветвь
на том же корне получает `resource_busy`, пока независимый узел выдаётся.
После принятия проверены backup, удаление G→N→корень, очистка маркера
из закрытой SQLite и нового backup, чтение новым процессом.

Полный локальный Windows `uv run --locked python -m tools.check --deliver`:
PASS, 662 теста, Ruff format/check, mypy для 186 файлов, 21 импортный
контракт, sdist и wheel. Перед итоговым прогоном один полный запуск обнаружил
регрессию `revalidate_result`: новая проверка собственного Work ошибочно
отказывала при изменившейся предпосылке, которую операция как раз должна
перепроверять. Проверка ограничена предками; прежние сценарии 3.5 и 3.6–3.7
повторены целевым Windows-прогоном. Отдельный повтор полного gate выполнен на
окончательном дереве.
