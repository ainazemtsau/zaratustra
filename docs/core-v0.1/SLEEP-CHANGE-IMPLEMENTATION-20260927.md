# Sleep и цикл изменения — рабочий пакет, 2026-09-27

## План и выполненный разрез

1. Добавить явный schema 11 к единому предметному SQLite и поставить исходный
   Sleep Method как точную версию обычного составного Work.
2. Сохранять границу поступления, область, обе позиции отбора, фактическую
   доставку, разбор, эффекты, остаток и общий ресурс исполнения. Дать обычному
   Pi доступ к чтению и записи через Core/Attempt/DBOS.
3. Сохранять адресный ChangeCandidate, план и результаты проверки отдельно от
   действующего Decision/Grant; применять точную версию Method/Binding в
   ограниченной области, останавливать новые использования и восстанавливать
   допустимое прежнее состояние с историей.
4. Проверить профильные сценарии, обычный Pi с localhost provider, полный
   gate и общий review. Итоговые результаты записаны в `RESULT.md`.

## Предметные записи

`initial_sleep_method()` поставляет Method v1 с обязательствами
`consolidation` и `exploration`. `zara_development.start_sleep` публикует эту
неизменяемую версию и создаёт обычный составной Work с двумя видимыми дочерними
Work. Запуск ручной. `SleepState` — адресуемый разбор этого Work, а не статус
исполнителя. Он фиксирует точный Method, область, границу поступления из
квитанции создания Work, позиции перечисления и исследования, выбранные
источники, подтверждённые стадии ContextManifest, анализ, фактически
сохранённые эффекты и остаток. `list_sleep_sources` выдаёт ограниченные порции
допустимой первички до зафиксированной границы; исследование обходит готовые
связи с уже выбранным. Материал вне связей и разговор без Work доступны.
Отсутствие находки отмечается `no_material`, а не выдуманной записью.

Расход Sleep складывается из фактических invocation всех членов составного
Work. Core проверяет общий лимит при допуске нового invocation. Новая сессия
видит этот же расход и сохранённый остаток; повтор операции с прежним ID
возвращает квитанцию. `SleepEffect` принимается только с точной уже
зафиксированной редакцией и её operation ID. Доставка источника принимается
только при соответствующем наблюдаемом ContextManifest и invocation.
Содержание источника открывается общими операциями памяти и текущими правами.

`ChangeCandidateState` содержит точную дельту Method либо Binding, прежнюю
версию/checksum, предложение и основания, ожидаемый результат, область и
исключения, затронутые Work, неизвестное, ValidationPlan, отдельные
ValidationResult и способ восстановления. Идею можно сохранить без плана;
такая редакция не применяется. Для регулярного допуска нужны сохранённые
положительные результаты по каждому критерию. Ограниченная trial допускает
явный предел использований и не превращается в регулярный допуск сама.
Семантическую полезность прозы Core не объявляет доказанной.

`ChangeDecisionState` — обычный Decision с текущим Grant, точной редакцией
кандидата, перечисленными результатами, режимом и областью. Сам кандидат
прав не создаёт. `apply_candidate` атомарно публикует точную версию и
записывает приложение с receipt, а не только пометку «принято». Для новой
версии Method требуется явный кандидат; исключение — точный исходный Sleep
Method v1. Новая Binding версия также проходит кандидата. Начатый Work
сохраняет закреплённый Method; новая версия влияет только на следующий
адресно созданный Work. Binding trial считает фактические срабатывания.

`stop_candidate` перекрывает новые применения в области, сохраняет реально
созданные Work и отдельно записывает их дальнейшую судьбу и внешние эффекты.
Для Binding он учитывает другие действующие области той же версии.
`restore_candidate` сверяет текущую версию, не стирает историю и не отменяет
начатые Work или внешний эффект. Binding восстанавливает прежнее определение
новой точной версией; Method вновь доступен для явного выбора прежней версии,
если она ещё существует и имеет нужный допуск. Невозможность вернуть
допустимость помечается `partial` с остатком. Поздний результат, включая
отрицательный, сохраняется отдельным событием с основанием; он не меняет
прошлое и не продлевает trial.

Schema 11 включает ревизии/ребра, приложения и события, фактические Work и
срабатывания, основание позднего результата и очередь удаления. Эти записи
проходят общие права, аудит, replay-квитанции, backup/restore и адресную
санацию. Удаление запрещённого основания делает зависимое содержание
недоступным, удаляет загрязнённые квитанции и помечает backup. Upgrade
выполняется явной Core-операцией из schema 10; подготовка Pi после
подтверждения `CONNECT` вызывает эту цепочку upgrade до текущей схемы.

## Обычный Pi

После выбора Core space:

1. `zara_development` с `mode=start_sleep`, описанной областью и конечным
   `resource_limit_units` создаёт Work и возвращает `work_id`/`sleep_id`.
2. Обычный `/zara-work` выбирает Work. Назначенные дочерние Attempt могут
   вызвать разрешённые `zara_memory` и `zara_development`; `read` и
   `enumerate` возвращают сохранённый прогресс и ограниченные источники.
   После прерывания новый процесс Pi выбирает тот же Work и продолжает
   оставшуюся часть с прежним расходом.
3. Поправка памяти идёт через `zara_memory`; кандидат, ValidationPlan и
   реальные результаты — через `zara_development.apply` с типизированными
   `create_development`/`revise_development`. `contract` показывает схему
   каждой операции. Decision и `apply_candidate` выполняются отдельно.
4. Следующий Work указывает допущенный Method `id@version@checksum`.
   `stop_candidate`, `record_change_outcome` и `restore_candidate` оставляют
   раздельные события; `application` показывает историю.

`tools.probe_development_pi --pi-runtime _scratch/pi-runtime` исполняет этот
путь с фиктивными данными и localhost provider через обычный Pi/DBOS,
проверяя фактические HTTP body и историю Core. Проба не является оценкой
качества выводов реальной модели или внешних последствий.
