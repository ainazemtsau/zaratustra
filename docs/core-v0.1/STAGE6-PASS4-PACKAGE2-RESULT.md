# Stage 6, проход 4, пакет 2 — живые окна DBOS/Pi

## Статус и границы

Владелец закрыл только техническое review пакета 1 на
`6deaaf17d8432db629ddfd788589087e28a13c2c` и разрешил пакет 2.
Независимая проверка Codex пакета 1: 60 профильных тестов, scoped gate и
три внешних аварийных сценария; полный gate 697 тестов был собственным
прогоном реализации пакета 1. Это не приёмка schema 7/8, прохода 3/4 или
Stage 6. Пакет 3 остаётся отдельным.

Этот пакет использует настоящие DBOS 3.0.0, обычный Pi 0.87.0 и фиктивный
localhost provider. Все пространства одноразовые, schema 8; Stage 5 и
pass 3 проверяются отдельно. `tools.probe_stage6_pass4` сохраняет JSON
публичного Core и DBOS, журналы runner, stderr Pi, RPC events и маркер
точки сбоя в `_scratch/pass4-package2-evidence-*/`. Состояние после аварии
читается новым Python-процессом **до** повтора. Число HTTP — запросы,
полученные локальным provider, а не доказательство внешнего результата.

В каждой строке ниже `claim`, `stop` и `assignment` обозначают публичные
`read_receipt`; `not_found` не означает удаления иной истории. `held` —
`read_execution.held_units`. У незавершённых случаев оба обязательства
родительского Method остаются `open`, его выходов нет: публикация ребёнка
сама по себе их не подтверждает и родителя не принимает. В параллельных
пространствах это `a_checked` и `b_checked`; в остальных — `checked` и
`final`. Каждый JSON-снимок содержит эти обязательства, выходы и ресурс.

Runner B затем создаёт собственный `claim`, один `answered` и выход. Повтор A/B не добавляет HTTP. У каждого ресурс свой; история одного не подменяет другого. |

Повтор runner выполняет один HTTP и заканчивает `stopped`, затем replay без нового HTTP. Причину прежнего самопроизвольного lock эта инъекция не устанавливает. |

`os._exit` — завершение процесса; потеря ответа provider — транспортный отказ;
`locking_mode=EXCLUSIVE` — управляемая конкуренция SQLite. Это разные
события. Каждая из трёх `os._exit`-инъекций записала маркер своей точной
границы. Обычный предметный отказ и `resource_busy` не выдаются за
доказательство восстановления после аварии. Транзакционный откат Core в
пакете 1 проверялся отдельно.

## Подтверждённый дефект и исправление

До исправления одновременный холодный старт A/B на общей DBOS SQLite
падал при миграции: в сохранённых журналах были `table workflow_status
already exists` и `no such column: workflow_status.queue_partition_key`.
Состояния обеих ветвей новым процессом сняты до повтора в
`_scratch/pass4-package2-parallel-cold-fixed/parallel/*/inspect-failed-before-retry.*`.
Первый вариант параллельной пробы имел ошибку настройки бюджета ресурса;
она исправлена в стенде и не приписана продукту. Контроль с заранее
инициализированной DBOS после исправления стенда прошёл с 2 HTTP.

Исправление продукта сериализует только короткое окно чтения существующего
workflow и `DBOS.launch()` между процессами одного Core space через
`managed_executor_start_lock`. Обычные Pi session locks, отдельные очереди,
DBOS workflow IDs и параллельное выполнение остаются адресными. Новый
межпроцессный pytest проверяет взаимное исключение startup lock без
сериализации сессий. Холодный живой контроль после исправления прошёл с
2 HTTP и точным повтором; последовательный запуск A→B и изоляция B также
прошли. Это не устанавливает причину прежнего Core `database is locked`.

## Открытые наблюдения

`database is locked`: старый независимый отказ возникал на Core
`PRAGMA application_id` во время `_record_stop`. Управляемый держатель
SQLite здесь воспроизвёл тот же стек и показал отсутствие частичного
предметного результата. В исходном случае неизвестно, какой процесс и
какой режим захватил Core SQLite; успешный повтор и исправление гонки
**DBOS** startup не закрывают это наблюдение. Первоначальная искусственная
проба сохранила exclusive lock после `ROLLBACK`, поскольку контекстный
менеджер `sqlite3.Connection` не закрывает соединение; её журнал и
снимок после выхода процесса оставлены в `_scratch/pass4-package2-core-lock/`.
Итоговая проба явно закрывает держатель до повторного запуска.

`rpc_transport`: прежний проход B оборвался в `_rpc_line` до первого HTTP
этого хода; старый журнал не сохранил stderr Pi. Здесь отдельная
последовательность A→B с захватом stderr Pi и JSONL RPC дала 2 HTTP и не
воспроизвела ошибку. Ни причина прежнего обрыва, ни отсутствие иных
расписаний не доказаны. Наблюдение остаётся открытым; успешный повтор не
назван исправлением.

## Проверки, атрибуция и предел

Собственные проверки исходной реализации: профильный межпроцессный pytest,
10 исходных живых сценариев, семь существующих Stage 5 fault-групп

probe (4 HTTP) и schema 8 A/B/P (3 HTTP, включая отдельное подтверждение,
backup/restore и удаление как регрессионную проверку неизменённого пути).
Последние операции не составляют пакет 3: его fault-матрица обслуживания и
установленный wheel не выполнялись. Полный Windows
`uv run --locked python -m tools.check --deliver` на окончательном коде:
**698 PASS** за 500.36 с, типы, Ruff, **21** импортный контракт, sdist и
wheel. Журнал: `_scratch/pass4-package2-deliver.log`. Это собственный
прогон реализации, не независимый review пакета 2.

Конечное число расписаний, фиктивный provider и управляемые failpoints не
доказывают exactly-once во внешней сети, причину двух прежних наблюдений,
все SQLite lock-перестановки или физическую сохранность при отказе диска.
