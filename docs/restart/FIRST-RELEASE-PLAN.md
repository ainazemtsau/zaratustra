# Первая рабочая версия Zaratustra

Редакция 2 · 16 октября 2026 года · конкретное задание перед разработкой.

Владелец согласовал усиление задания: «Подготовь конкретные контракты, что переносим и как проверяем, и покажи мне итог, чтобы уже переходить к разработке без нового круга обсуждений». Здесь зафиксированы технические решения и условия их проверки. Это разрешение на подготовку задания; реализация и реальные модельные вызовы ещё не запускались.

Этот файл — единственный редактируемый план первой поставки. [Исследование](REPORT.md) остаётся свидетельством своей редакции. Для первой поставки этот план уточняет его контракты и исправляет сужение Sleep. Solmax хранит текущие допуски и ссылки, а не независимо редактируемую копию технического плана.

## 1. Результат и границы

Человек приходит с любой Activity обычными словами. Zaratustra использует уже известное, выясняет только недостающее, выбирает достаточную организацию работы и помогает получить результат с меньшей нагрузкой на человека. Просьба начать практику не превращается в обязательный проект по созданию процесса. Планирование является полезным результатом тогда, когда оно нужно для самого запроса.

Первая поставка обеспечивает создание Activity, полезную работу, поправки, сохранение и продолжение, память, полный начальный Sleep, диагностику и установку. Модель определяет смысл; код обеспечивает идентичность, версии, формы, права и допустимые переходы. Нет предметных исключений для YouTube, обучения или тренировок.

Технические решения, выбранные в этом задании для итогового согласования:

- Один локальный экземпляр; Python + SQLite; отдельный устанавливаемый пакет ядра.
- Pi — первый полноценный клиент. Независимый технический клиент проходит тот же контракт без Pi.
- Работа при открытом клиенте или явном запуске. Продолжение сохраняется, постоянный daemon не требуется.
- Существующий Git-репозиторий сохраняется. Разработка — в отдельной рабочей копии и ветке codex/restart-first-release; новая поставка не использует старый runtime.
- Новое явно выбранное хранилище. Старые установки, незавершённая 0.26.0 и личные данные сохраняются. Автоматического импорта нет.

Полный второй пользовательский адаптер, веб-клиент, несколько хостов-писателей, постоянный фон, marketplace, массовая миграция и автоматическая установка кода через Sleep не входят. Ядро может развиваться через отдельную проверяемую разработку; эти ограничения не объявляют его навсегда неизменяемым.

## 2. Граница реализации и зависимости

Исходная исследованная база: продукт 0.25.5, schema 18, Git 9d903d709783601c4878b707b9618031753a6854. Текущая незавершённая 0.26.0 не является стартовым доказательством. Перед первым кодом исполнитель сверяет свежую историю, фиксирует base и манифест разрешённого переноса. Изменение base с новым поведением требует отдельной оценки, а не незаметного включения чужого diff.

Предлагаемое расположение в той же Git-истории:

~~~text
packages/core/
  pyproject.toml
  src/zaratustra_core/
    api.py, types.py, errors.py
    store.py, commands.py, permissions.py
    records.py, artifacts.py, attempts.py
    maintenance.py
packages/app/
  pyproject.toml
  src/zaratustra_app/
    coordinator.py, context.py, executor_port.py
    cli.py, diagnostics.py
    adapters/pi/
    methods/
tests/restart/
  contract/, failures/, adapter/, usefulness/
docs/restart/
  <точная утверждённая версия этого плана и фактический возврат>
~~~

Список модулей определяет ответственность, а не обязательный файл на каждую функцию. Внутри границ допускается объединить соседние малые модули; менять направление зависимостей нельзя.

Пакет приложения зависит от публичного API ядра. Адаптер вызывает координатор/публичный API; ядро не импортирует приложение, Pi, прежний пакет zaratustra, DBOS или SQLAlchemy. Методы ассистента — версионируемые ресурсы приложения/записи, доступные по точной ссылке. Пакет ядра устанавливается отдельно, импорт не запускает процессы, не создаёт пространство и не открывает пользовательские данные.

Это явное изменение упаковки прежнего продукта: два поставляемых пакета вместо обязательной зависимости всего продукта от старого окружения. Внутри новой установки есть один backend. Существующий продукт в старой рабочей копии остаётся отдельным сохранённым предшественником. До решения о замене кандидат имеет отдельную команду zaratustra-next и явный data-root.

Для первой сборки фиксируются проверенные версии Python/Pydantic/SQLite и локальные проверки возможностей SQLite. Старая установленная DLL, PATH, домашние конфиги и установленный продукт не могут быть скрытыми prerequisites. Pi и его способ доступа объявлены только для Pi-профиля. При отсутствии выбранного доступа нет автоматического платного fallback.

## 3. Владельцы данных

Логические сущности ниже не требуют отдельного сервиса или таблицы для каждой строки.

| Данные | Единственный владелец и правило |
|---|---|
| Пространство, instance_id, recovery_epoch, права | Ядро. Права меняются отдельным адресованным действием через действующий допуск |
| Activity и её именованные записи | Ядро: устойчивый ID, область, объявленный ключ, одна текущая ревизия и история |
| Сообщения, вопрос, обработанная граница | Ядро: исходные bytes/blocks, подтверждённое происхождение, последовательность, точный reply_to |
| Work и Attempt | Ядро: работа, попытки, точные входы, ожидание, поколение исполнения и продолжение |
| Результат и его принятие | Ядро хранит результат и отдельное принятие его точной версии; успех инструмента не создаёт принятие |
| Память и Method | Те же версионируемые записи ядра с источниками, областью и явным статусом применения |
| Артефакты | Удержанные неизменяемые bytes с digest; ядро хранит точные ссылки и права |
| Внешний вызов | Ядро владеет намерением и наблюдениями; фактический внешний эффект принадлежит внешней системе |
| История Pi, cache, обзоры | Производные/внешние материалы с указанным охватом; не второй current предметного состояния |
| Код, Git и внешние файлы | Соответствующее внешнее хранилище. Activity ссылается на точный commit/hash, не ведёт вторую карту кода |

Уникальность current задаётся по (space_id, activity_id либо space-scope, record_kind, declared_key). Модель получает каталог существующих ключей до создания новой записи. Ядро запрещает два current для одного ключа, но не узнаёт автоматически, что weekly-plan и schedule означают одно. Смысловое объединение выполняется явным изменением с сохранением происхождения.

Record содержит ID, kind, key, revision, body, optional schema_ref и source_refs. Свободный текст допустим. Для объявленных структур используются нейтральные типы из прежнего конечного формата: text, boolean, integer, decimal-string, date, datetime с timezone, enum, exact-ref, object, list; обязательность, nullable и пределы явные. Дубликаты полей, неизвестные типы, нечисловые decimal, NaN/Infinity и неявное приведение строк к bool/int отвергаются. Формат не проверяет истинность, полезность, причинность или качество цели.

## 4. Общий контракт команд C0

Все операции ниже — проект нового публичного API, а не утверждение, что они уже реализованы.

**Запрос.** contract_version, instance_id, space_id, recovery_epoch, command_id, operation, payload, expected_heads; при необходимости action_id и confirmation_ref. Principal и происхождение ввода берутся из доверенного соединения/клиента, а не из полей, предложенных моделью. Transport request ID не заменяет command_id.

**Намерение.** Валидный запрос получает fingerprint по фиксированному wire/v1: поля операции, область, epoch, ожидаемые версии и payload; principal привязывается отдельно. Ключи объектов сортируются, порядок списков сохраняется, Unicode и строки не нормализуются; числовые поля envelope — целые, decimal представлены строкой. Исходный пользовательский текст удерживается отдельно точными bytes. Векторы сериализации входят в контрактные проверки обоих клиентов. Transport ID, время повторной доставки и смена credential при том же principal не меняют намерение.

**Повтор.** command_id устойчив до первой отправки и сохраняется в очереди доставки клиента. Для уже зафиксированной команды тот же ID/намерение возвращает ту же квитанцию без нового эффекта; иное намерение даёт conflict. Чужой principal или отозванное право чтения не получают содержимое старой квитанции. Новый транспортный ID не создаёт новую предметную команду. Для внешнего действия дополнительно уникален action_id в его области: новый command_id не обходит уже известный эффект.

**Версии.** Запись проверяет expected_heads внутри транзакции. Исторический exact ref остаётся историческим; роль must_be_current требует текущей ревизии на admission. Самостоятельного перебазирования смысловой правки адаптером нет. При конфликте исходные материалы сохраняются, выполняется новое чтение и формируется новое намерение.

**Ответ.** receipt_id, command_id, outcome, exact result refs, committed sequence и безопасный diagnostic_id. Отказ содержит code, адрес поля/ссылки и retry_policy: never, same_id, after_refresh или reconcile. Базовые классы: invalid_request, denied, wrong_instance, stale_epoch, stale_basis, identity_conflict, idempotency_conflict, unsupported_capability, resource_exhausted, outcome_unknown. Пустой успешный текст не заменяет ошибку.

**Данные и права.** Все writers используют этот API. Адаптер модели не имеет произвольного SQL/file-доступа к внутреннему хранилищу и capability принятия владельцем. Владелец может заранее делегировать ограниченные операции с памятью/методами. Адресное подтверждение связывает digest показанного изменения, область и ограничения; одноразовое разрешение расходуется атомарно с admission. Текст tool output не становится подтверждением. Локальная доверенная UI/CLI-граница проверяется отдельно; эти гарантии не защищают от произвольного процесса с полным доступом к файлам и credentials ОС.

**Чтение.** Snapshot имеет revision/cursor и явные ограничения объёма; страницы относятся к одному snapshot. Exact read возвращает указанную версию либо missing/denied, без подстановки latest. Проверяются текущие права. Инструкции доступны по закреплённой версии; операции, отсутствующие в describe_contract, не рекомендуются как рабочие.

## 5. Операции и атомарные результаты

| Контракт | Существенный вход | Проверки и сохранённый результат |
|---|---|---|
| C1 describe_contract / read_snapshot / read_exact / lookup_receipt | Версия контракта, scope, cursor либо exact ref/command_id | Проверка доступа; capabilities, текущие головы, доступные действия и причины отказов. Readiness и admission используют один вычислитель предпосылок; запись повторяет его внутри транзакции |
| C2 ingest_message | conversation_id, stable client_event_id, исходные blocks/attachments, optional reply_to(wait_id, revision) | Доверенное происхождение; точное совпадение при retry. Одна транзакция: message + sequence + receipt + durable intent обработки. Свободное сообщение не закрывает «последний вопрос» |
| C3 apply_changes | Непустая ограниченная группа typed create/update/tombstone предметных записей, expected_heads, exact refs; optional initial_work; для tool call — сохранённая корреляция Attempt | Права, уникальные ключи, формы и ссылки. Изменения + новые ревизии + audit + receipt + связь tool call с receipt + initial_work/его intent коммитятся вместе. Обязательное поле initial_work не навязывается каждой поправке |
| C4 open_work | Цель работы, scope, method_ref, required input refs, предел ресурса, continuation policy | Права, существующие exact refs и допустимый тип выполнения. Сохраняет Work и intent подготовки. Sleep использует ту же операцию с методом Sleep |
| C5 prepare_attempt | work_id, expected work revision, исходный processed cursor, непрерывный input range/cutoff, input manifest, profile_ref, лимиты | Manifest различает exact и must_be_current; диапазон начинается после исходного cursor и не пропускает вход. Фиксируются Attempt, граница входа, версии Method/профиля, обязательные bytes/refs и intent dispatch. Нельзя начать при отсутствующем обязательном материале |
| C6 claim_dispatch | attempt_id, action_id, expected generation, executor identity, верхняя граница ресурса вызова | Текущие права, epoch, основания и единственный claim. Атомарно сохраняет claim и резерв ресурса до внешней отправки. Неопределённый исход удерживает резерв; новый ID не разрешает повтор |
| C7 observe_attempt | attempt/event ID, raw event/artifact ref, наблюдаемое external correlation, usage и при сверке exact reconciliation evidence | Авторизованный исполнитель; дедупликация событий и проверка соответствия свидетельства заявленному профилю внешней системы. Удерживает terminal/progress/unknown/результат сверки и intent обработки. Поздний fenced ответ сохраняется как late evidence, не меняя current |
| C8 commit_outcome | attempt + terminal ref, expected heads/generation/исходный cursor, exact outputs, разрешённые typed changes, wait либо next_work/closed, processed cutoff | Проверка происхождения terminal, прав и оснований. Одна транзакция: изменения + result/final + статус Work/Attempt + CAS обработанной границы + wait/продолжение + receipt. Нет пропусков, регрессии cursor и поглощения сообщений после pinned cutoff |
| C9 control_work | work_id, pause/resume/cancel, expected revision | Сохраняет управление и поколение исполнения. Старый исполнитель теряет право публиковать current. Отмена внешнего действия — наблюдаемый запрос; уже отправленное не считается отозванным задним числом |
| C10 grant / revoke / confirm_change / accept_result | Точная область/дельта либо версия результата, действующий источник полномочия | Отдельные операции доверенного управления; модель не назначает principal. Revoke до admission блокирует новое действие. Принятие фиксируется отдельно от результата |
| C11 stage_artifact / export_diagnostics | Bytes и digest/тип; либо безопасный диагностический scope | Bytes удерживаются долговечно до публикации ссылки; запись БД не ссылается на незавершённый файл. Диагностика работает без модели, preview предшествует передаче, секреты и тексты разговоров по умолчанию исключены |
| C12 backup / restore_quarantined | Явно выбранное пространство/backup, manifest и новое место | Согласованный snapshot и manifest артефактов; проверка hashes, integrity, foreign keys. Restore создаёт изолированную копию с новым epoch и без исполнения. Включение эффектообразующего исполнения требует отдельного выбора единственного активного экземпляра и прекращения старого |

C3 и typed changes в C8 разрешают только предметные записи Activity, данных, памяти, Method и их ссылок. Через них нельзя записать grants, acceptance, receipts, provenance человеческого ввода, epoch или системные статусы исполнения. Такие поля меняются только соответствующим проверенным переходом C2/C4–C10/C12. C3 и C8 используют одну реализацию этих ограничений; запрещённая дельта отвергает весь набор атомарно. Координатор не дублирует SQL-переходы. C10 не прячется в универсальный произвольный invoke. Физическая схема БД остаётся внутренней, но её ограничения unique/CAS проверяются напрямую независимыми тестами.

C5 закрепляет полный непрерывный диапазон новых входных сообщений от сохранённого cursor до cutoff. C8 продвигает cursor CAS-переходом только по этому диапазону. Если часть входа не обработана, нельзя продвинуть границу через неё: выбирается более короткий непрерывный префикс либо сохраняются исходная граница и явное pending-продолжение. Cursor отмечает завершённую обработку по заявлению модели; он не доказывает понимание текста.

Каждый tool call внутри Attempt до выполнения получает сохранённую корреляцию (attempt_id, native_tool_call_id) → command_id/action_id. Связь выполненного действия с receipt фиксируется вместе с действием. После сбоя сначала читается эта receipt; повтор callback не создаёт новую команду. Журнал выполненных/неопределённых инструментов включается в восстановление и вход следующей попытки. Это предотвращает повтор одного вызова, но не обещает автоматическое распознавание двух разных смыслово одинаковых запросов модели.

Ресурс Work не сбрасывается при reopen или новой Attempt. C6 резервирует верхнюю границу в реально контролируемых единицах; для неизвестного usage резерв не освобождается. Следующий admission учитывает известный расход и все неразрешённые резервы. Retry C6 не резервирует повторно. Число вызовов ограничивается всегда; денежный/token-предел заявляется только при поддержке проверяемого ограничения выбранным executor. Неподдержанное ограничение даёт unsupported_capability до запуска.

На одну Work допускается одна активная Attempt; в первой версии одна conversation не исполняет два диалоговых turn параллельно. C5 захватывает соответствующий слот CAS-переходом. Для terminal result действует уникальность (attempt_id, result_slot): другой command_id не создаёт второй final. Повтор с тем же содержимым возвращает прежний исход; конфликтующее содержимое не затирает его. Неопределённая предыдущая отправка блокирует автоматическую новую попытку того же действия до reconciliation.

| Переход | Разрешённая операция и смысл |
|---|---|
| Новая Work → ready | C3 initial_work или C4; есть сохранённое продолжение подготовки |
| ready → running | C5 готовит Attempt; C6 фиксирует единственный claim и резерв |
| running → waiting / ready / completed | C7 удерживает terminal, C8 сохраняет адресный вопрос / продолжение / конечный выход. completed означает выход ограниченной работы, а не принятие или доказанную полезность |
| running → blocked | Исход внешней отправки неизвестен либо есть неустранённое техническое препятствие; причина и действие сверки сохранены |
| ready/running/waiting/blocked → paused или cancelled | C9; сохраняет причину и повышает поколение исполнения. Статус не утверждает, что внешняя система уже остановилась, и не стирает unknown внешнего эффекта |
| paused → ready | C9 resume после проверки исходов и ресурса; unknown не превращается в готовность повторить вызов |
| blocked → ready / running | C7 сохраняет доказанную сверку, C9 resume проверяет поколение, права и ресурс. ready допустим при доказанном безопасном новом admission; running — для наблюдения уже существующего внешнего исполнения без повторного send. При удержанном terminal выполняется C8 |
| waiting → ready | Адресный ответ C2 сохраняет intent; координатор проверяет нужный wait и основание. Произвольный текст другой роли не подменяет ответ |

Ресурс исчерпан при незавершённой работе — paused с остатком, либо blocked при неизвестном расходе/исходе; completed недопустим. Статусы Attempt выводятся только из этих проверенных событий, а адаптер не записывает их произвольно.

Между подготовкой и dispatch проверяются новые входы и текущие основания. Если до отправки появился новый необработанный ввод, контекст пересобирается. Уже запущенная попытка может вернуть ответ по прежней границе: поздний ввод остаётся необработанным и порождает следующее продолжение. До его рассмотрения новое зависимое внешнее действие не запускается. Явная отмена через C9 блокирует старую публикацию независимо от текста диалога.

### Обязательные атомарные границы

1. Вход: message + processing intent + receipt.
2. Изменение: current revision + история + audit + receipt; при создании Activity — также выбранная первая Work.
3. Dispatch: единственный claim/action identity и резерв ресурса фиксируются до внешнего вызова.
4. Выход: изменения + final/result + processed cutoff + wait/continuation + receipt.
5. Одноразовое разрешение: расходование связано с тем admission, который оно разрешает.

Ожидающие intents лежат в той же SQLite и обнаруживаются при старте. Уведомление ускоряет работу, его потеря не теряет продолжение. Первая версия сохраняет журнал idempotency без очистки, меняющей гарантии повторов.

Recovery различает intent без claim и зафиксированный claim без доказанного исхода. Второй случай считается потенциально отправленным даже при отсутствии записи send: unknown/reconcile, без автоматической повторной отправки. Повтор внешнего вызова допустим лишь по проверяемому idempotency/reconciliation-контракту принимающей стороны; его отсутствие не обходится новым ID. Транзакции и writer-lock не удерживаются во время ожидания модели, человека или внешней системы; idle client не держит snapshot/transaction.

Файл и SQLite не объявляются одной транзакцией: immutable artifact сначала записывается, синхронизируется и проверяется, затем публикуется DB ref. Незадействованный staged файл допустим; опубликованная ссылка на недолговечные bytes — дефект. Согласованный backup удерживает/пинит набор referenced artifacts до окончания копирования.

## 6. Обычная работа от запроса до восстановления

Пример проверочной трассы, не пользовательская специализация: «Есть десять минут, потренируем разговор в отеле. Начни без плана и карточек».

1. Pi-адаптер удерживает event ID и точный исходный ввод. C2 сохраняет сообщение M20 и intent; только затем возвращается подтверждение.
2. Координатор читает snapshot, доступные Activity/ключи и уместную память. На новой Activity достаточно минимально нужной договорённости; готовый семираздельный шаблон не обязателен.
3. C4–C6 сохраняют попытку A1 с cutoff=20, фактическими входами, методом и доступными инструментами. Модель получает исходный запрос, а не только его summary.
4. Модель выбирает смысловую структуру. Через C3 создаются Activity и первая работа; через обычный путь начинается сама практика. Допустимые локальные изменения не требуют согласования каждой записи.
5. При вопросе C8 фиксирует wait W7 и адресуемую причину ожидания. Ответ связывается с W7 через C2; чужой/устаревший wait не закрывается.
6. Полученные результаты и фактические затруднения удерживаются через C7, затем C8. Успешная запись не означает «пользователь принял».
7. Пока A1 работает, приходит M21: «Теперь только пять минут». Ответ A1 может завершить обработку до 20, но не до 21. Изменение получает своё продолжение; следующая зависимая работа учитывает новый предел.
8. Закрываем клиент и очищаем его локальную историю в тестовом окружении. Новый клиент читает то же пространство и продолжает с актуальным wait/результатом/ограничением. Если raw terminal уже удержан, повторяется обработка, а не inference.
9. Технический клиент без Pi выполняет ту же трассу. Предметные IDs, версии, права и причины отказов совпадают с учётом заявленных возможностей клиента.

~~~mermaid
sequenceDiagram
  participant U as Пользователь
  participant A as Адаптер
  participant K as Ядро
  participant C as Координатор
  participant M as Исполнитель модели
  U->>A: Исходный запрос
  A->>K: C2 ingest_message
  K-->>A: Квитанция после commit
  C->>K: Snapshot, C4–C6, pinned inputs
  C->>M: Точный вход и ограниченный запуск
  M-->>C: Исходный terminal
  C->>K: C7 удержать terminal
  C->>K: C8 результат и продолжение
  K-->>A: Сохранённый результат / адрес вопроса
~~~

При stale_basis retained output не применяется к новому current. Сначала новое чтение; механическое повторение обработки того же terminal не делает новый model call. Если нужна содержательная переработка, это новая явно учтённая попытка с новым основанием и ресурсом, а не скрытый retry.

## 7. Sleep через те же контракты

Sleep — обязательная возможность первой версии. Запуск «Sleep» не требует от человека выбирать проблемы. Метод получает доступную область и конечный ресурс из действующих настроек/прав. Если необходимого лимита или права нет, уточняется именно оно.

Sleep — обычная Work с exact Method, Attempt, входами и продолжением. Отдельных базы памяти, исполнителя или конкурирующего статуса SleepRun нет. Специфический прогресс хранится в версионируемой записи, связанной с Work.

| Шаг метода | Что сохраняется и как продолжается |
|---|---|
| 1. Восстановить положение | Work, версия Method, остаток, действующие права/ресурс и результаты предыдущих изменений |
| 2. Выбрать порцию | Верхняя граница поступлений, позиция перечисления, selected refs; отдельно coverage исследования вне известных связей |
| 3. Поддержать память | Разбор обычной, успешной и неудачной работы; фактические необходимые поправки, неопределённости и связи через C3/C8 |
| 4. Выбрать вопросы | Модель сама выбирает вопросы и ограниченную попытку сопоставления вне готовых связей; жалоба не обязательна, находка не гарантирована |
| 5. Проверить основания | Exact источники/фрагменты, наблюдение/утверждение/гипотеза, альтернативы, контрпримеры, прежние отрицательные попытки |
| 6. Изменить или предложить | Разрешённая поправка применяется; повторяемый метод получает новую версию/область/проверку; недостаточные права оставляют предложение |
| 7. Доставить последствие | Следующая подходящая Work получает актуальную память/Method. Её реальные outcomes связываются с изменением для последующей оценки |
| 8. Сохранить границу | Что разобрано, фактически изменено, предложено, осталось неизвестным/незавершённым; причина остановки и продолжение |

Минимальные поля прогресса: work_id, method_ref, scope, source_high_watermark, enumeration_cursor, selected_source_refs, delivered_manifest_refs, analysis_result_refs, unexplored_coverage_position, applied_receipts, proposed_changes, remaining_refs/условия возврата, consumed_resource и unresolved_calls. Отдельного поля «всё осмыслено» из одного курсора нет.

Перечислено, выбрано, доставлено и разобрано — разные события. Удержанный analysis_result — утверждение модели о разборе, а не программное доказательство понимания. Завершение ограниченного прохода не объявляет всю среду изученной. Позднее поступление остаётся новым входом даже при описании старого события.

Разрешённая обычная поправка памяти не требует обязательного кандидата. Новая инструкция/Method может применяться в заранее делегированных пределах после соразмерной проверки. Изменение кода ядра — отдельная разработка с адресуемым patch/build, проверкой и установкой. Метод не меняет собственные полномочия и источник принятия.

Исчерпание ресурса сохраняет остаток. Любой следующий внешний вызов проходит C6; восстановление не обнуляет расход. Если usage неизвестен, он остаётся unknown, а не нулём. Число summaries и предложений не является показателем пользы: оцениваются результаты следующих работ, включая основание сузить или отменить метод.

## 9. Проверки, которые могут опровергнуть решение

Oracle — небольшая независимая таблица ожидаемых ID, версий, входных hashes, прав и эффектов. Он не импортирует production-функции допуска/контекста/recovery. При crash результат читается новым процессом. Строки — семейства сценариев, не план раздуть число тестов.

| G15 Artifacts и maintenance | Fault при staging; backup со связными bytes; повреждённый backup; restore в новую область без исполнения | Ref до durable bytes, неполный manifest, active restore со старыми полномочиями. Broken ref, утрата bytes или разрешённый старый epoch — fail |

Отказ, вызванный ожидаемым отсутствием Pi в G1, является дефектом независимости. Ошибка сборки произвольного мутанта не доказывает предметную проверку. Для засчитанной поломки нужны: корректный baseline, достигнутая injection, падение конкретного поведенческого assertion и воспроизводимый trace. Survived mutation и невалидный mutant учитываются раздельно. Автоматическая mutation-библиотека полезна дополнительно; архитектурные поломки задаются адресно.

Механические части проверяются детерминированно без модели. Смысловые части G12–G14 требуют отдельно разрешённого live profile и предела ресурсов: заранее успешный текст provider не доказывает самостоятельный выбор вопросов и полезность. Неожиданный запрос выбирается в рамках возможностей первой версии; отсутствие непредусмотренного внешнего инструмента не объявляется дефектом общей архитектуры.

| B. Полное продолжение | Расширение проверок A на остальные поддержанные pause/cancel/reopen, вопросы, исправления, неизвестные исходы и retained terminal. Расширяется покрытие G7–G11; падения фиксированной трассы A не переносятся в B |
| C. Память и Sleep | Версии, полный метод §7, доставка изменений и outcome feedback. Механические G12–G13, затем разрешённая содержательная оценка |
| D. Поставка и проверка полезности | Установка собранных пакетов вне checkout в чистом профиле поддержанной Windows, diagnostics preview, G14–G15, отдельная проверка существенных гарантий и показ владельцу |

Проверки атомарности, прав и входов не откладываются до D. Технический кандидат со stub не называется доказанной полезной версией.

Первая команда исполнителю после разрешения реализации — пакет A. Она включает фиксацию base/manifest, два независимых пакета, один сквозной путь без legacy, actual receiver evidence и проверяемые аварийные окна. Работы по B–D входят в тот же согласуемый объём первой поставки; промежуточный показ не выдаётся за окончательное принятие. Один исполнитель владеет изменяемым кодом; параллельные помощники могут проверять независимые утверждения.

Останавливаем расширение и исправляем причину, если:
- путь требует скрытого старого координатора, старых данных или ручного SQL-ремонта;
- второй технический вход не способен продолжить то же состояние;
- новый предметный запрос с имеющимися средствами требует исключения в ядре;
- retained input/result не доходит до следующей работы;
- проверка пропускает соответствующий заведомо сломанный вариант;
- Sleep приходится сокращать до summaries, жалоб или одних кандидатов ради завершения.

Существенное изменение контракта, стека, первого клиента, безопасности или обязательного результата возвращается владельцу с конкретным препятствием. Локальные детали кода, имена вспомогательных функций и выбор параметризованных тестов не требуют нового обсуждения.

## 11. Что считается завершением

Возврат исполнителя содержит exact commit/build, manifest зависимостей и переноса, версии контракта/методов, traces двух клиентов, результаты gates и mutant diffs, среду установки, отдельно live-model evidence и ограничения. Отчёт об успешных тестах не заменяет файлы/логи, по которым вывод воспроизводится.

Существенные гарантии проверяет отдельный свежий проверяющий по закреплённой версии. Исследовательские помощники этого чата являются pre-pass и не заменяют такую проверку реализации. Владелец получает пригодную установку и понятный показ; техническая исправность и принятие полезности фиксируются отдельно.

Код допускается по конкретной версии этого задания. Реальные модельные вызовы требуют выбранного доступа и конечного ресурса; личные данные, публикация, переезд старой установки и передача Solmax под управление продукта не входят автоматически. Эти границы не требуют повторного обсуждения назначения продукта.

После принятия первой версии отдельная реальная Activity ведёт одно разрешённое улучшение Zaratustra до изменения кода и проверки. Полный переезд Solmax следует из пригодности в работе, а не из наличия карточки Activity.
