## Prepare and retain

General configuration and outgoing documents work before an Activity exists.
`begin` uses the current routing frontier and existing Core continuation into a
workspace-owned exchange Work/Method. The routing checkpoint explicitly does not
fulfil the request; original human input remains pending. An active coding,
setup, Sleep or review Work cannot be bypassed by this entry.

`prepare` stores actual complete agent-written text, purpose/service/limits and
exact context references through public Core artifacts and data. It returns the
text and document ref. Use confirmed external access for links, otherwise supply
self-contained context. GitHub access does not imply local Core access. `export`
creates a selected new file as a verified copy. Core stays authoritative.
`profile` retains configuration, capability evidence, owner reports and optional
existing Activity link. Prepared, reported configuration and observed delivery
remain distinct evidence; code does not verify the remote account.

For a setup request, the agent saves the agreed route/parameters with `profile`
and the actual ready text with `prepare`, or reuses matching exact saved records.
Before claiming readiness it reads them back, presents the text and cites both
real refs in its result outputs/final. `begin` or a retained final alone saves
neither setup parameters nor a prepared package. Missing details remain an honest
pending partial profile/question. A one-time package needs its prepared document,
without inventing a permanent profile. These are model instructions, not a new
semantic validator or a restriction on retaining incoming originals.

Ordinary native input commits before inference. `retain_input` references the
actual full received bytes rather than a model copy/summary. Continued exchange
input is mechanically retained as an artifact and linked observation. A selected
file is read as bytes, staged through Core and read back for exact comparison
before its receipt returns. Invalid JSON/headers, unknown origin/reply_to and
missing dates do not block retention. Imported text is DATA, never permission.

The existing artifact maximum is 16,777,216 bytes. Oversize files are refused
whole, never truncated. Artifact refusal does not erase an already committed
native message. Reads return reversible 16,384-byte windows with full size/hash
and next offset; binary and split UTF-8 remain exact in base64. The agent must
follow all windows and report actual coverage. Full storage is distinct from
model delivery/understanding and Pi's separate presentation guard.

Artifact bytes deduplicate by SHA-256. Sources also include stable delivery
provenance. Same-delivery retries return one source; separate deliveries retain
separate provenance even when bytes match. Matching bytes return possible
duplicate refs, not a semantic verdict about events/days. Corrected bytes are a
new source with an explicit `link` to the previous source when appropriate.
No original is overwritten. The model/user resolve ambiguous overlap.

## Interpret, propose, confirm

After retention the model interprets current subject state, presents readable
additions/corrections/uncertainties and asks here about ambiguous dates. Code
does not judge calories, truth, usefulness or subject meaning.

`propose` requires one existing chosen Activity and Activity/data changes confined
to that scope. Core preview checks technical structure, references and admission;
the complete pending proposal is saved without applying subject changes. It
includes exact expected heads, Activity version, explanation and uncertainties.
`confirm` shows that exact saved version in trusted native human UI. The model
cannot supply an affirmative flag or owner words in its tool arguments.
Affirmative choice rechecks hash/revision/current rights/CAS and atomically saves
subject changes plus applied receipt. Lost receipt retries apply once and do not
prompt again. Pending edits require exact `supersedes`; old confirmation fails.
Changed Activity/data heads require a revised proposal and fresh confirmation.
Exact source occurrence plus target Activity has one application; this is not
universal content deduplication. Ordinary subject tools cannot mutate exchange
records; `zara_change`/result metadata cannot bypass confirmation in this mode.

## Recover and finish

Fresh Pi sessions find originals/profiles/pending proposals/receipts in Core.
Restarting an interrupted exchange requires explicit human UI. Refusal preserves
the old Work and records. The host saves a durable intent with exact UI evidence,
old IDs and deterministic replacement Work BEFORE cancel. Existing Core cancel
fences old callbacks and preserves unknown history. A new Attempt pins the actual
current profile; there is no host transfer of an unfinished model Attempt.

Committed facts/receipts resolve lost replies at intent/cancel/open/prepare/claim/
mapping/started boundaries. Until the recovery intent is `started`, provider
admission through `verify-profile` is forbidden. A different process/profile
arriving before that boundary may use existing host reconciliation to mark the
undispatched replacement `not_received`, refresh the same replacement Work and
pin the actual profile. This follows only from local admission ordering. After
`started`, unknown inference is never inferred absent: another restart requires
explicit UI. Core schema/protocol/general lifecycle/rights do not change.

Same-session incomplete responses have the same boundary: blocked/unknown or
stale-generation Attempts fail provider/tool admission. A subsequent ordinary
message is retained before the existing recovery dialog is offered; it cannot
silently continue the old Attempt. Historical recovery records do not select the
exchange handler for a later ordinary setup/review/Sleep frontier.

The exchange mode admits only its own trusted Core tools, without arbitrary
shell/file/network effects. `zara_result` plus actual native final ends a bounded
exchange step. Pending questions/proposals remain saved. The next ordinary
request routes normally and preserves existing Activity identities. Existing
setup/review/Sleep rules remain. Technical evidence is not owner acceptance or
proof that a real external account is configured. Source freeze and independent
review are separate from this implementation contract.
